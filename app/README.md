# app/ — the platform, the features and the profiles

A server-rendered web app is a **profile**: a selection of **features** composed on a **platform**,
built into one self-contained binary. The server is Odin, the HTML is generated by Odin procedures,
HTMX is the only front-end library, and every asset is compiled into the binary and served from
memory. There is no NPM and no bundler; the build is `odin` through one script.

Three profiles ship today:

| Profile | Features | Store | Theme | What it is |
|---|---|---|---|---|
| `skeleton` | dashboard, gallery, contacts, about | SQLite | full (6 styles × 23 schemes) | the 1.2.x contacts console at its exact URLs: the worked example and the performance witness |
| `minimal` | home, notes, about | memory (no SQLite library at all) | lite (one style, two schemes) | the one-page starter: a notes card added to over HTMX |
| `lab` | lab, about | memory | full | the stream contract pages: SSE, WebSocket and multipart from Odin to htmx 4's extensions (M2; scripting and compat follow) |

## Run it

You need the [Odin compiler](https://odin-lang.org) (dev-2026-10) on your `PATH` and, for a SQLite
profile, **a C toolchain**: `prepare` compiles the SQLite amalgamation into a static library.

- **Windows**: MSVC **Build Tools** (`winget install --id Microsoft.VisualStudio.2022.BuildTools -e`,
  the *Desktop development with C++* workload), run from an *x64 Native Tools* prompt; or clang with
  `llvm-lib` on the `PATH`. Git for Windows supplies `brotli` and `gzip` for the bundled assets.
- **Linux**: `sudo apt-get install -y clang brotli` (clang links Odin and compiles SQLite).
- **macOS**: `xcode-select --install`, and `brew install brotli`.

```sh
app/prepare.sh              # once: htmx, SQLite, each profile's bundled assets  (app\prepare.bat)
./build.sh skeleton         # build a profile into app/bin/skeleton             (build.bat skeleton)
app/run.sh                  # build and serve skeleton on http://127.0.0.1:8080  (app\run.bat)
PROFILE=minimal app/run.sh  # the minimal profile instead
```

`prepare` is idempotent and cheap after the first run; `NO_SQLITE=1` skips the SQLite step (a memory
profile needs none). `run` serves a SQLite profile from a local `data.db` seeded with the demo rows;
`DB_PATH=:memory:` gives a fresh store per process. `OPEN=1` also opens a browser tab; a port argument
or `PORT` overrides 8080.

`build.sh <profile>` (`build.bat` on Windows) is the one place a profile's build flags live: its four
family collections, `-vet -strict-style -warnings-as-errors` with the further vet flags, `VERSION` (sent as `x-version`) and the
directory its bundled assets are embedded from. `CMD=check|test|run` swaps the odin command; extra
arguments go to odin (`-o:speed`, `-define:TEST_ROUTES=true`).

## The layout

```
app/
  cmd/<profile>/     brand.odin main.odin routes.odin routes_test.odin: a profile, all hand-written
  features/<f>/      a feature: f (the domain), models/, views/, web/, and storetest/ where it has a store
  stores/<family>/   each feature's store in the family: sqlite/<f>/ (with migrations/) and memory/<f>/
  platform/          the layers every profile shares (below)
  vendor/odin-http/  the vendored HTTP server fork (UPSTREAM.md names its base and every change)
  prepare.*  run.*   setup and the dev loop
```

**The platform's layers** (each a package; a layer imports its own and the ones below):

| Layer | Packages |
|---|---|
| L1 | `sys` (the OS edge: traps, the open-file limit, clocks), `sqlite` (the binding), `ext` (htmx extensions), `escape` (`esc`, `url_encode`, `json_esc`) |
| L2 | `store` (+ `store/sqlite`: store v3, the writer task, migrations, `--backup`; `store/memory`), `env` (the typed environment), `authz` (+ `authz/anonymous`), `obs` (logfmt, metrics, health), `guard` (crash containment, the watchdog), `workers`, `markdown` |
| L3 | `web` (router, `front`'s helpers, responses, assets, the platform's routes), `stream` (SSE, WebSocket and multipart on the fork's streams), `hub` (topics, rings and `/events`), `html` (the layout and components), `client/*`, `theme/*` |
| L4 | `app` (the `front` chain, `boot`, `check`, `serve`, `wait`, `shutdown`; only `cmd/*` imports it) |

**A feature** is a set of packages: `models` (types and the store contract), `f` (the domain:
validation and rules, plain values and errors, never HTTP), its store in each family, `views` (HTML
builders) and `web` (handlers, `ROUTES`, `init`). A feature reaches another only through its domain.
Only `platform/web` imports odin-http; it re-exports `web.Request` and `web.Response`.

**A family** is a build-time choice of one implementation, picked by `build.sh`'s collection flags:
`store:` (sqlite or memory), `identity:` (who the viewer is), `client:` (the behaviours: vanilla, or
hyperscript, which `lab` uses; markup names them through `html.behave`) and `theme:` (full or lite). `--features --json` prints what a binary was built with.

## What's inside `skeleton`

| Page | URL | Shows |
|------|-----|-------|
| Dashboard | `/` | stat cards counted from the store, sparklines, links, a live "ping" fragment |
| Components | `/components` | buttons, badges, avatars, progress, tabs, accordion, modal, drawer, toasts |
| Forms | `/forms` | inputs, select, range, switch, radios, inline validation; a submit creates a contact |
| Data & CRUD | `/data` | a sortable, paginated table over SQLite; create, edit, cycle, delete |
| About | `/about` | what this is, and the source |

Search lives in the top bar and as plain JSON: `curl 'http://127.0.0.1:8080/api/search?q=grace'`.

## How a request is served

`front` (app/platform/app/front.odin) runs every request in one order: the host and route, the
request id and the security headers; a malformed `Content-Length` refused with 400; the `*.fly.dev`
301; the cross-site write guard; the body cap and the 405/404 for an unrouted path; the viewer and the
route's permission; the body under the route's cap; the handler inside the crash guard; one logfmt
access-log line. Writes to the SQLite store queue on the writer task, which commits whatever is queued
in one transaction, and the handler answers through a deferred response once its batch commits.

A crash in a handler that touched nothing shared answers 500 and serving goes on; one that held a
lock, posted an operation or was inside SQLite drains and exits 70, and a stalled loop exits through
the watchdog (D15). `/healthz`, `/livez`, `/readyz` and `/metrics` report on it.

## Dependencies

- [Odin](https://odin-lang.org): the compiler.
- [odin-http](https://github.com/laytan/odin-http), vendored with the fork's changes (F-1…F-17:
  streams, the crash-guard hook, timeouts, the connection cap, bounded shutdown, deferred responses).
- [HTMX](https://htmx.org) 4.0.0: the only front-end library, pinned by SHA-256.
- [SQLite](https://sqlite.org) 3.53.4 for a SQLite profile: the amalgamation, pinned by SHA-256 and
  compiled by `prepare` with the starter's flags.

## Notes and non-goals

- Plain HTTP on loopback; TLS is the proxy's job (see `infra/PLAN.md`).
- With `DB_PATH=:memory:` the data resets with the process; point `DB_PATH` at a file to keep it, and
  back a live one up with `<binary> --backup backup.db` (`docs/DATA.md`).
