# S0.8 Caddy and streams

**Closes:** whether Caddy's `encode` delays SSE events or multipart chunks (03 §8) · **Pass criterion:** a native
`caddy run` (dev tool, no Docker): events and parts arrive ≤ 50 ms after the write, with spark's `encode zstd gzip` and
without; decide the matcher
**Result:** PASS with a change: through spark's `encode zstd gzip` every event and part arrived ≤ 19.4 ms after the
write (p99 ≤ 4.6 ms) on a quiet box, against ≤ 9.8 ms without it, but compression holds 1.1 to 2.8 MiB of Caddy's
memory per open stream, so streams opt out with `Cache-Control: no-transform` and no Caddyfile matcher is needed ·
**Date:** 2026-10-26 · **Commit:** ddfff0f

## Decision

**Caddy's encoder doesn't delay streams.** `reverse_proxy` flushes after every upstream write for `text/event-stream`
and for any response without a Content-Length, and `encode`'s flush flushes the zstd or gzip encoder first (Caddy
2.11.7, `modules/caddyhttp/encode/encode.go`, `reverseproxy/streaming.go`). Measured from Node and from Chromium, with
zstd and gzip: within about 1 ms at p50 and 3.5 ms at p99 of the same runs without `encode`; the worst event, 19.4 ms,
came with 100 compressed streams at once. A WebSocket through the same site gets no encoder at all.

**Streams still go out uncompressed.** The four reasons, in order of weight:

1. **Memory.** A compressed stream holds its encoder in Caddy for its whole life: 2.8 MiB per open stream with zstd,
   1.1 MiB with gzip, against 65 KiB uncompressed (500 open streams). 1000 streams through spark's `Caddyfile.prod`
   (stage 3) would hold about 2.7 GiB.
2. **Caddy's choice is erratic for multipart.** It decides on the first write: a multipart stream whose first part
   is 512 bytes or less goes out raw, a bigger one compressed (`minimum_length` 512). SSE is always compressed.
3. **Small events grow.** gzip makes 40-byte SSE events 25 % bigger on the wire (each flush adds a sync block); zstd
   saves 38 %.
4. **One compression context per stream.** Every event of a stream compresses against the earlier ones, so another
   user's text (a chat line) and this user's data share a dictionary: the precondition of BREACH-style length attacks
   (reasoning, not measured).

The cost is bandwidth: 1 KiB HTML fragments shrink about 40× on a long stream. Streams carry small fragments, and the
uplink is not a binding trigger (D41), so that's accepted.

**The matcher is a response header, not a Caddyfile block.** Every stream response sends
`Cache-Control: no-cache, no-transform` instead of `no-cache`. Caddy's `encode` skips any response whose Cache-Control
holds `no-transform` before it looks at the type (`isEncodeAllowed`); measured: identity through spark's
`encode zstd gzip`, 67 KiB per stream, same delays. The header lives in `platform/stream` next to
`X-Accel-Buffering: no`, so one place covers every proxy that honours RFC 9111's `no-transform`, and spark's
`Caddyfile.prod` runs unchanged at stage 3. Rejected: a Caddyfile `match` block. Caddy's response matcher can't
negate a value (`header` only tests a field's absence with `!`), so leaving out two types means listing every other
compressible type (site `matcher` in [S0.8/Caddyfile](S0.8/Caddyfile), 17 lines) and keeping that list in step with
Caddy's default list by hand. It works (measured) but it is a second definition that drifts.

**Caddyfiles for M2 and M3.** The stack Caddyfile (§20.4) is unchanged and keeps no `encode`; its `(app)` snippet was
measured as site `stack` and passes. A Caddy that compresses, i.e. stage 0's optional `tls internal` Caddy for h2 and
stage 3's `Caddyfile.prod`, uses plain `encode`; streams opt out by their header:

```caddyfile
https://localhost:8443 {
	tls internal
	# streams send Cache-Control: no-transform, which encode honours (S0.8): no match block
	encode zstd gzip
	reverse_proxy 127.0.0.1:8080
}
```

**Folded into PLAN §8.2, §20.4, §20.6, D12 and D41 on 2026-10-26**, as proposed here:

- PLAN §8.2 and D12: "Every stream response sends `X-Accel-Buffering: no` and `Cache-Control: no-cache,
  no-transform`, so nginx (NPM) flushes each event (08 §3.2) and no proxy compresses a stream: a compressed stream
  costs Caddy 1.1 to 2.8 MiB, and Caddy's `encode` honours `no-transform` (S0.8)."
- PLAN §20.4, the "No `encode` anywhere" bullet, and D41's last paragraph: replace "(S0.8 checks the encoder)" and
  "(whether Caddy's encoder delays multipart chunks is spike S0.8)" with "(S0.8: the encoder adds no delay, but streams
  opt out with `no-transform`, so a Caddy that compresses, such as stage 3's `Caddyfile.prod`, needs no matcher)".
- PLAN §20.6: after "`Caddyfile.prod` unchanged", add "(its `encode zstd gzip` skips streams by their `no-transform`,
  S0.8)".
- M2's headers spec asserts both stream headers on SSE and multipart responses; `e2e-proxy` asserts
  that SSE and multipart come back without `Content-Encoding` through the repo Caddyfile and NPM's config.
- 03 §8, §12 and 08 §3.3: the `encode` question is closed (the research notes are local).

## Method

- **Box:** the dev PC, Windows 11, 8 cores and 16 threads, 64 GB, everything on loopback. Other agents
  ran builds, WSL2 and browsers at the same time (box CPU 5 to 100 %).
- **Caddy** v2.11.7 `windows_amd64` (Go 1.26.8, klauspost/compress v1.20.1) from the GitHub release; the zip's SHA-512
  matched `caddy_2.11.7_checksums.txt`. Run natively:
  `S08_STORAGE=<scratch dir> caddy run --config docs/spikes/S0.8/Caddyfile --adapter caddyfile`, one site per case:

  | Site | Port | What |
  |---|---|---|
  | `plain` | 18781 | `reverse_proxy` with its defaults |
  | `spark` | 18782 | spark's site shape: `encode zstd gzip`, then `handle { reverse_proxy … { header_up X-Real-IP {client_ip} } }` |
  | `stack` | 18783 | D41's `(app)` snippet (no `encode`; `flush_interval -1`, `stream_close_delay 5m`, health checks) |
  | `matcher` | 18785 | `encode zstd gzip` with a `match` block that lists compressible types without SSE and multipart |
  | `tls` | 18786 | `tls internal`, no `encode` (h2 to the browser) |
  | `spark-tls` | 18784 | `tls internal`, `encode zstd gzip` (h2; Chromium offers zstd there) |

  The internal CA is never installed in a trust store (`skip_install_trust`; the clients ignore the certificate).
- **Server:** the stream prototype on the vendored fork, with S0.8's changes, in [S0.8/server](S0.8/server): each SSE
  event, multipart part and `/ws/tick` frame carries `t=<unix µs>` taken just before `stream_write`; `pad=` adds a
  compressible HTML fragment (small: 40-byte SSE events, 127-byte parts; 1 KiB); `nt=1` sends `no-transform`; `/now`
  gives the clock. Built with Odin dev-2026-10 (`84bc3fc`):
  `odin build docs/spikes/S0.8/server -collection:vendor_fork=app/vendor -out:s08.exe -o:speed`, run as
  `s08.exe 18780` (4 loops). The fork commits that landed during the runs (3c07c77, 370fb13, 196b646) leave
  `stream_write` and its send path unchanged.
- **Delay** = arrival after decoding − write time. The client's clock is aligned to the server's by the `/now` sample
  with the smallest round trip (about 0.3 ms), so values near 0, or slightly below, are within that error.
- **Node client** ([measure.mjs](S0.8/measure.mjs), Node 22.16, `zlib` zstd and gzip decoders), driven by
  [run.sh](S0.8/run.sh): per site, SSE and multipart 1 × 1000 events 10 ms apart (Windows timers make it 15.6 ms),
  small and 1 KiB; 200 fresh streams × 3 events, 10 at a time (the first event's delay); 100 concurrent streams × 200
  events. `Accept-Encoding: gzip, deflate, br, zstd` (Chromium's; Caddy picks zstd) and `gzip, deflate` (gzip). Multipart
  is read as hx-multipart reads it: a part counts when its `Content-Length` bytes are in. WebSocket: `/ws/tick` pushes
  and `/ws/echo` round trips through `spark`.
- **Rounds.** Three rounds at normal priority (no repeats), then two at High priority: the server and Caddy raised
  with PowerShell's `PriorityClass = 'High'`, the client with `PRIO=high ./run.sh`. In the High rounds a run whose box
  CPU (all cores, over the run) passed 50 % was repeated, up to 3 tries; the quietest try counts (110 kept of 122
  runs, box CPU 7 to 55 %). A cell's p50 is the median of the rounds, its p99 and max the
  worst round. [tables.mjs](S0.8/tables.mjs) makes the tables from [S0.8/results](S0.8/results).
- **Browser** ([browser.mjs](S0.8/browser.mjs)): Chromium 153.0.8010.12, headless, Playwright 1.63 from `e2e/`. On
  each site's `/page`: EventSource, fetch-streamed SSE (htmx 4's hx-sse reads the body itself) and fetch-streamed
  multipart, 500 events 10 ms apart, and 50 fresh streams for the first event; WebSocket `/ws/tick`. Three rounds at
  normal priority, one at High (the browser's own process tree only). `spark-tls` was also run with `--disable-http2`.
- **h2 without Chromium** ([h2.mjs](S0.8/h2.mjs)): `node:http2` through `spark-tls` and `tls`, 300 events, 2 runs.
- **Memory** ([mem.mjs](S0.8/mem.mjs)): 500 open streams through one site (a 1 KiB event per second), Caddy's Go heap
  in use from its admin `/metrics` after two forced GCs, before and with the streams open.

## Caveats

- One box, Windows, loopback. apollo's Caddy runs on Linux in Docker behind NPM; that path is M2's `e2e-proxy` job and
  M3's 1 h soak. Whether NPM's nginx gzips `text/event-stream` or `multipart/mixed`, and whether it would hold events
  if it did, is **UNVERIFIED (M2 `e2e-proxy`)**.
- Whether other proxies honour `no-transform` (nginx's gzip, Cloudflare) is **UNVERIFIED**; only Caddy 2.11.7 was
  measured. The memory figures are Caddy 2.11.7's encoder settings and may move with a Caddy bump.
- The normal-priority tails (up to 205 ms) come from the shared box; the High-priority rounds isolate Caddy from it.
  apollo's own numbers are M3's.
- Chromium only, headless. Firefox and WebKit through Caddy are M2's (`e2e-proxy`, Firefox in CI). The 15.6 ms h2 tick
  was seen only on Windows; whether Chromium on Linux or macOS has it is **UNVERIFIED (M2)**. Any latency assertion in a
  browser spec over h2 on Windows has to allow for it.
- The release's cosign signature was not checked, only the SHA-512 against the checksums file.
- The BREACH point is reasoning, not a measured attack.
