# S0.5 Workers and argon2id

**Closes:** the login flow off the loops is unverified (07 §5.2) · **Pass criterion:** fresh timings (3 presets,
n = 10); pool + `next_tick` reply + generation check: a disconnect mid-hash causes no use-after-free under ASan;

the timings pass and ASan passes with a fork change (F-13) and pools that drain first at shutdown · **Date:**

## Decision

The login flow runs off the loops as planned, with one fork change and one change to the drain order; the storm budget
needs restating.

1. **F-13, deferred responses, joins the fork** (`S0.5/fork.diff`: a new 108-line `deferred.odin`, 21 lines in
   `server.odin` and `response.odin`, and its `UPSTREAM.md` row). The fork as it is never frees a connection whose
   handler returned without answering: no read is posted, so a client that leaves goes unnoticed until the reply's
   send fails, and a raw `^Response` happens to stay valid (`s05-asan-nof13` below). That is an accident of a missing
   feature, and an abandoned request holds its connection and its verify to the end. F-13 adds the watch that closes
   such a connection early, and with it the generation check. A handler that answers from a pool calls
   `http.response_defer(res, on_gone, job)` and returns. The worker posts the job back with
   `nbio.next_tick_poly(job, done, l = ref.loop)`, and `http.response_resume(ref)` there returns the Response, or nil
   when the connection is gone or serves another request. The ref is (loop, socket, a per-thread request generation):
   the check is a lookup in the thread's connection map and never reads freed memory. While a response is deferred, a
   poll on the socket notices a client that leaves: the connection closes at once and `on_gone` tells the
   application, which skips the hash if the job is still queued. The query, llama and jobs pools use the same calls.
2. **The pools drain at the start of shutdown, before the loops wait on their requests.** ASan found a second hazard
   that no generation check covers: a worker that finishes after its loop has left posts into a dead event loop. The
   target's queue fills first ("operation queue on event loop filled up"), then nbio's `wake_up` faults. So each pool
   stops intake and cancels its queue from `on_thread_shutdown` (F-4); every reply then lands within one job (one
   verify), and each loop waits for the replies it is owed (F-13's count, bounded by `drain_deadline`).
3. **Parameters: `PARAMS_OWASP` (19 MiB, t = 2, p = 1) stays the default.** Its verify took 19–32 ms here (medians,
   both OSes, a busy box), two at once barely slower; the pool of 2 serves about 80 verifies/s. `PARAMS_OWASP_SMALL`
   (7 MiB, t = 5) is a little faster and OWASP rates it equivalent, but the larger memory is the better defence against
   GPU guessing, so it stays the fallback for a tight `mem_limit`. The 64 MiB preset (t = 3, p = 1) took 119–191 ms
   here and is out: it misses the 100 ms target on this CPU already. Whether apollo verifies OWASP in ≤ 100 ms
   is **UNVERIFIED (M4)**: `--hash-password` should print its own derive time, so Alex's bootstrap step measures it.
4. **Each worker keeps one buffer for argon's memory** (`derive(..., allocator = arena over the buffer)`). It was faster
   in 5 of 6 OWASP rounds (by 3–24 %) and slower in one noisy Linux round, so the speed is not the reason: it fixes the
   pool's memory at threads × 19 MiB, with no 19 MiB heap allocation per login.
5. **§18.4's login-storm budget fails as written, and the plan should restate it (Alex's call).** On the pool a
   verify never blocks a loop, but a hash costs a core, and a relative +10 % on a sub-millisecond p99 is less than a
   busy neighbour core costs. Proposed: size the pool by CPU (`ACCOUNTS_ARGON_THREADS` 1 when the container has ≤ 2
   CPUs, as apollo's `full` does, so hashing never takes more than half the quota; 2 above that); state the storm budget
   in absolute terms (under `cpus: 2.0` with one argon thread: other routes' p99 ≤ base + 0.5 ms, measured here at
   +0.08–0.12 ms on the quieter host; the cgroup never throttled; every login answered 200/401, or 503 at once past
   the queue); and keep the per-client login limits (§17.5) in front, so 50/s can only come from many clients. Under
   `cpus: 2.0` two argon threads got the cgroup throttled in up to 92 % of its periods, and a lower thread priority
   only starved the logins.

## Method

**Box.** The dev PC: Ryzen 7 5800X (8 cores, 16 threads), Windows 11, and Ubuntu (WSL2) on the same CPU. Other agents
used the box throughout (the Windows host sat at 22–99 % CPU), so each comparison is relative and interleaved. Odin
dev-2026-10 (`84bc3fc`) on both; clang 18 for ASan; k6 v2.0.0 (the linux-amd64 release, checksum checked) inside WSL2.

**Files** (`docs/spikes/S0.5/`):

| File | What it is |
|---|---|
| `bench/main.odin` | argon2id: n verifies per preset, one thread and two at once, memory fresh or reused |
| `server/main.odin` | the prototype: `/ui/ping` (the skeleton's fragment), `POST /login` on the argon pool, `GET /stats` |
| `server/sched_*.odin` | the workers' priority (`ARGON_SCHED`) and the `PIN=1` placement, per OS |
| `fork.diff` | F-13 against `app/vendor/odin-http`, with its `UPSTREAM.md` row; `git apply` from the repo root |
| `build.sh` | the Linux builds: release, release on the fork as it is, and three ASan variants |
| `asan.sh`, `load/disconnect.py` | clients that leave mid-verify, then SIGINT while verifies are in flight |
| `load/p99.js`, `load/p99.sh`, `load/p99.ps1` | `/ui/ping` at a fixed arrival rate with and without logins, arms interleaved (Linux, Windows) |

**Timings.** `odin build bench -o:speed`, then `bench 10` on Windows and in WSL2, three rounds alternating the two, with
the host's CPU sampled each second. A row is 10 verifies after one warm-up (20 when two threads run at once; both
count). "Fresh" lets `derive` allocate its memory from the heap each time; "reused" gives it a per-thread buffer.

**The pool.** `ACCOUNTS_ARGON_THREADS` workers (2) take jobs from a ring of `ARGON_QUEUE` (32) under one mutex; a full
ring answers 503 `busy, retry` with `retry-after: 1`. The handler reads the body, copies the password into a heap job,
calls `response_defer` and submits. The worker verifies into its reused buffer and posts the job back with one
`nbio.next_tick_poly(job, on_verified, l = job.loop)` (at most 2 posts in flight, far below nbio's 128-slot ring).
`on_verified` calls `response_resume`, answers 200 or 401 (503 if the job was cancelled and the client is still
there), frees the job, and ends with `free_all(context.temp_allocator)` (§5.4). `on_gone` marks a queued job
cancelled, so the worker posts it back without hashing.

**ASan.** `build.sh` makes three `-o:speed -debug -sanitize:address` builds: `s05-asan` (F-13 with the generation
check), `s05-asan-nogen` (F-13's watch, but the reply answers through the raw `^Response`: the negative control) and
`s05-asan-nof13` (the fork as it is, with the raw pointer, as in 12 §4's prototype). `asan.sh` runs one with 4 loops,
then `disconnect.py`: 40 threads for 10 s, each posting a login on a new connection, then 70 % leave after a random
0–300 ms (half with FIN, half with RST) and 30 % read the answer and send a `/ui/ping` on the same connection. Last, a
1 s burst where every client leaves within 50 ms, with SIGINT 0.3 s into it. Three verify costs: the real OWASP verify
(about 0.6 s under ASan), and `FAKE_HASH_MS` 25 and 120 (a sleep in the hash's place: the OWASP and 64 MiB costs at
full speed). `ASAN_OPTIONS=detect_leaks=0:halt_on_error=1`. 3 rounds of each.

**p99.** Each run starts a fresh release server with `THREADS=2` and sends `/ui/ping` at a fixed 2,000/s (5 s
warm-up, 15 s measured; a fixed arrival rate, so a slower loop shows as latency and not as fewer requests) and, in the
login arms, 50 `POST /login`/s for the whole run. A capacity probe put the two loops' knee near 20,000/s on Linux.
Arms: `base` (no logins), `pool` (2 argon threads), `pool1` (1 thread), `idle` and `idle1` (the same under
`SCHED_IDLE` on Linux, `THREAD_PRIORITY_IDLE` on Windows); the arms alternate and their order rotates each round. The
settings:

- **WSL2, 4 vCPUs** (`p99.sh`): the server under `taskset -c 0-3` (apollo has 4 hardware threads), k6 under
  `taskset -c 4-15`.
- **WSL2, `cpus: 2.0`**: the same inside a `systemd-run` scope with `CPUQuota=200%`, as compose limits `full`; the
  cgroup's `cpu.stat` gives the throttled periods. One more set at 10 logins/s (`RATE=10`).
- **Windows, High priority** (`p99.ps1`): the server on logical CPUs 0–3 and k6 on 4–15, both in the High priority
  class, so the other agents' Normal-priority work can't preempt them.

CPU busy % comes from `/proc/stat` per CPU group, the process times on Windows, and the host's
`\Processor(_Total)\% Processor Time`. Other agents loaded the host (22–99 %) and at times the VM itself. A WSL2 run
counts as disturbed, and is left out, when the VM's CPUs outside the server's were more than 15 % busy (k6 alone used
5–9 %): another workload was sharing the VM. The settings were run again when the host got quieter. A first attempt at
5,000/s and 30 s gave the `inline` reference (the verify on the loop).

An earlier matrix, before the pool drained at shutdown, found the second hazard: `s05-asan-nof13` with the real verify

deferred). The negative control at 25 ms ran clean too: with OWASP costs a reply comes back within about 0.4 s, inside
the fork's 500 ms close delay, so the raw pointer finds a closing connection, not freed memory. That bug would be rare
in production, which is why a check that does not depend on timing matters.

The fork moved on while this ran (`bb4a901`: header-phase peers close at drain, `stream_end` takes a deadline).
`fork.diff` applies there with offsets only, and one more round of each verify cost on that fork ran clean (1,670 left
while deferred, 0 reports); the negative control aborted again.

the fourth deferral still saw its client leave after three polls on that socket had been removed (nbio warns that
Windows delivers one poll per socket).

What the numbers say:

- **The pool keeps the loops free.** With the verify on the loop, ping p50 went to 0.6 s and p99 to 7–32 s. On the
  pool, ping p50 moved by at most 0.04 ms in every setting.
- **The hashes still cost the tail, by the CPU they take.** 50 OWASP verifies/s are 1.2–2.5 cores here. Where they
  share CPUs with the loops, ping p99 grows: +24 % on Windows with the server's 4 logical CPUs at High priority, +49 %
  in WSL2 on a quieter host, ×7.7 on a busy one. At a 0.4 ms p99, +10 % is 40 µs, less than a hashing neighbour core
  costs: no setting met it.
- **Under `cpus: 2.0`, two threads get the cgroup throttled.** They kept it throttled in up to 92 % of its periods
  (×22 on a busy host, +97 % on a quieter one). One thread was never throttled (+25 % on the quieter host, ×2.7 on the
  busy one) but serves only about 35 verifies/s, so 20–56 % of the storm got 503. 10 logins/s on two threads: +20 %,
  never throttled.
- **A lower priority is not the fix.** `SCHED_IDLE` did not help under the quota (×38: the throttling is the cgroup's,
  whatever the priority), and on Windows the idle workers kept the tail at +5 % only by starving: 66 % of logins got
  503 and a verify took 103 ms.
- The busy-host numbers are the host's contention as much as the design's; the quieter rows are the better estimate.
  A run with the loops and the workers on separate vCPUs (`PIN=1`) was disturbed in 5 of 6 runs and is left out.

## Caveats

- apollo's verify time is **UNVERIFIED (M4)**; the dev PC is a newer, faster CPU, and the `cpus: 2.0` quota was only
  modelled with a cgroup in WSL2.
- The box was busy throughout: the p99 comparisons are relative, from interleaved rounds, and the quieter-host rows
  have 3–4 runs each. Whether one argon thread holds p99 ≤ base + 0.5 ms on apollo is **UNVERIFIED (M4's
  login-storm gate)**.
- On Windows k6's clock steps by about 0.5 ms (p50 and p90 read 0), so the Windows p99s compare how many requests
  cross that step, not their exact latency.
- F-13 is a spike: M1 adds its tests (a stale ref after fd reuse, a pipelined request behind a deferred one, `on_gone`
  under the guard). A deferred response has no deadline of its own: a job that never comes back holds its connection
  until the client leaves or the drain deadline. The watch starts only if no body read is in flight when the handler
  defers; `front` reads the body before routing, so that holds for the planned handlers.
- The guard (F-5, S0.6) did not wrap the worker task or `on_verified` here; §10.2 makes both entry points.
- Windows connections all land on one loop (03 §2.1), so the cross-loop reply path was exercised on Linux only.
