# S0.7 Drain and restart

**Closes:** 13 §4.1's unbounded waits · **Pass criterion:** exit ≤ 6 s with 500 SSE + 500 WS + a slowloris + a half body +
a stuck idle peer; WS got 1012; the bind retry succeeds after `kill -9` at 0/50/100 ms
**Result:** PASS with a change: exit in 5.62–5.66 s on both OSes, 500/500 WebSockets got 1012 and 500/500 SSE streams got
their `retry:` event, and every restart after `kill -9` served; two refinements to F-9 were needed to get under 6 s ·
**Date:** 2026-10-26 · **Commit:** 3c07c77 (ddfff0f plus the two F-9 refinements below)

## Decision

PLAN §8.7's sequence holds, with two refinements to F-9 (now in `app/vendor/odin-http/server.odin` and its
`UPSTREAM.md`), and one rule for the app's `main`:

1. **A connection still reading its request line or headers closes at once at drain, like an idle one.** No handler
   runs yet, so nothing is lost; before this, a slowloris counted as an active request and waited out the 5 s deadline.
2. **Past the drain deadline, connections already closing no longer hold the loop** (their 500 ms close delay exists
   so a peer can read the last response; at the deadline that no longer matters).
3. **Nothing in `main` may wait on its own after the server returns.** The first rounds exited at 6.17–6.28 s: the
   harness joined its watchdog thread, which sleeps a second between checks. The drain's bound runs to the process
   exit, so `app.shutdown()` (§8.7 steps 6–7) must not join sleeping threads; it signals them and exits.

With these, the worst case is the half-sent body: an active request gets `DRAIN_DEADLINE_MS` (5 s), then the loop exits
within one 100 ms shutdown tick, and leftover operations get at most 500 ms. That is 5.6 s, under compose's 10 s
`stop_grace_period` and Fly's 10 s `kill_timeout`, as §8.7 needs. §8.7's table gets one line for refinement 1 ("a
connection still reading its headers closes with the idle ones"); its step 5 stays as it is.

F-12's bind retry is confirmed useful: without it, one Linux restart in nine failed with `Address_In_Use` 100 ms after a
`kill -9`; with it, every restart served, on both OSes. 13 §3.3 left the cause UNVERIFIED and this spike doesn't settle
it; it shows the retry covers it.

## Method

- **Server:** S0.6's `guardlab` (`S0.6/guardlab/`) on the vendored fork, 4 loops, `-o:speed`; it raises its open-file
  soft limit to the hard limit at boot (§8.6 step 2; WSL's default soft limit, 10240 here, is enough for this test but
  the default 1024 of a login shell would trip F-8's cap first). Its `/sse` holds a stream whose `on_shutdown` writes
  `retry: <500–3000 ms jitter>` with a `data:` line; its `/ws` holds a WebSocket whose `on_shutdown` sends close 1012;
  `/body` reads a request body.
- **Driver:** `S0.7/drain.mjs` (Node 22, raw sockets).
  - drain: 500 SSE and 500 WebSocket clients, a slowloris (headers sent one line every 2 s, never ended), a half body
    (`Content-Length: 1000`, 500 bytes sent), and an idle peer (one request on a kept-alive connection, then it stops
    reading and never closes); 1.5 s later the server is told to stop: SIGTERM on Linux (F-10), `/admin/shutdown` on
    Windows (no SIGTERM there; the route calls the same `server_shutdown`). Measured: signal to process exit (the
    client sees the child exit), the close code each WebSocket got, and whether each SSE stream got the `retry:` event.
    Three rounds per OS.
  - rebind: a server with 20 SSE streams open is killed with SIGKILL (`taskkill /F` on Windows); a new one starts on
    the same port 0, 50 and 100 ms after the old one is gone; with F-12's 3 s retry and with it off
    (`BIND_RETRY_MS=0`). Linux three times, Windows once.
- Windows 11 native; Linux on WSL2 (the server in WSL, the driver on Windows over WSL's loopback forwarding).

## Results

| Run | exit | WS 1012 | SSE `retry:` |
|---|---|---|---|
| Windows, before refinements 1–3 | 6.17 s | 500/500 | 500/500 |
| Windows, refinements 1–2 only (the harness still joins its watchdog) | 6.25, 6.26, 6.28 s | 500/500 ×3 | 500/500 ×3 |
| Windows, all three | 5.64, 5.62, 5.64 s | 500/500 ×3 | 500/500 ×3 |
| Linux (SIGTERM), all three | 5.64, 5.66, 5.66 s | 500/500 ×3 | 500/500 ×3 |

Every round exited 0 with all 1000 streams open at the signal (the server's own count: `sse=500 ws=500`).

| Restart after `kill -9` | 0 ms | 50 ms | 100 ms |
|---|---|---|---|
| Linux, bind retry 3 s (3 runs) | 3/3 served | 3/3 | 3/3 |
| Linux, retry off (3 runs) | 3/3 | 3/3 | 2/3: one `could not listen …: Address_In_Use`, exit 1 |
| Windows, retry 3 s | served | served | served |
| Windows, retry off | served | served | served |

## Caveats

- On Windows the drain was started by a route, not a signal, so F-10's SIGTERM path is verified on Linux only; Windows
  services and containers aren't a target (§20).
- 13 §4.1's 13.2 s exit came from a pending 15 s app timer. Here the app cancels its per-loop timers in
  `on_thread_shutdown` (F-4), and F-9 caps whatever is left at 500 ms; an app timer that is never cancelled still delays
  the exit by that much, not by its own length.
- The idle peer that never answers the FIN is closed by the server after the 500 ms close delay, whatever the peer does;
  this spike checks the server's exit, not the peer's view.
- The cause of `Address_In_Use` after `kill -9` (13 §3.3) stays UNVERIFIED; it reproduced once in nine.
