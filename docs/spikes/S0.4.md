# S0.4 `:memory:` parity

**Closes:** D17 · **Pass criterion:** candidates A, B, C on every `:memory:` cell with sort indexes, both legs; pick the
first passing one, else Q6
**Result:** FAIL, so Q6 applied: no candidate passes every `:memory:` cell on both legs. C passes the most and Alex
chose it (Q6, answered 2026-10-26): `pages@mem` and `list@mem` on both legs and `write@mem` on Linux are gated against
HEAD, each with a documented exception · **Date:** 2026-10-26 · **Commit:** the candidates are ddfff0f's patches
(`S0.4/candidates/`), built by `S0.4/build.sh` on 196b646's fork for the first rounds and on 575f5c7's (F-7's sweep)
for the re-runs; the harness is S0.1's at 1005402

## Decision

**The `skeleton` profile's `:memory:` mode is C**: store v3 with the sort indexes, `MEMMODE=ephemeral` on an unsynced
temp file (on `/dev/shm` on Linux), and group commit of request writes through the writer task. The file DB takes C
too (X17; R2a): v3 alone writes at 0.38× v1.1.1 on a file DB, C at 2.8–4.3×. Folded into PLAN §11.1, §11.3 and §18.3,
D16 and D17, and ANSWERS round 5.

C misses three `:memory:` store cells against max(HEAD, v1.1.1), each by 3–9 %, and wins each against HEAD by far
(median of the paired ratios, n = 5):

| Cell | Linux vs max | Windows vs max | vs HEAD (Linux, Windows) | Why it misses |
|---|---:|---:|---|---|
| `pages@mem` | 0.95 | 0.96 | 2.64, 2.44 | v1.1.1 sorts its 20 rows in Odin from RAM; C reads them through SQLite on a per-loop reader |
| `list@mem` | 0.93 | 0.94 | 3.95, 3.70 | the same |
| `write@mem` | 0.91 | 1.20 (passes) | 0.98 (Linux) | on Linux tmpfs, v1.1.1's in-RAM insert is cheaper than a WAL append, even batched; on Windows the batching wins |

These are Q6's documented exceptions: M1's `tests/parity-waivers.txt` lists each with this record as its reason, and
the gate reads those three cells against HEAD (the pass rule otherwise unchanged). No file-DB cell is waived, and C
passes every file-DB store cell on both legs (Results). The light routes, `static` and `seo`, gate against HEAD alone
(Q35; S0.1), where C on the sweep build reads 0.98–1.05 (S0.2).

What building and measuring them showed, now in PLAN and DECISIONS:

- **B's `synchronous=OFF` was not new, and on Windows B is v3 plus the indexes.** Research 12's "v3 ephemeral" column
  already ran its temp file unsynced, and under WAL `NORMAL` never syncs a commit. B's one new lever is tmpfs on
  Linux, and it didn't save B's writes: `write@mem` 0.28 on Linux.
- **C makes the write handlers asynchronous.** A write handler returns unanswered and a continuation answers from the
  loop's `next_tick` after the batch commits. M1 builds it on F-13's deferred response, whose generation check makes a
  connection cut while its write is queued cost a map lookup (S0.5), which the spike's patch lacked.
- **C's writer has no timer.** It commits whatever is queued as soon as it is free, up to 100 per transaction; a 10 ms
  tick would add up to 10 ms to every write. D16's writer task now reads the same.
- **A changes what a client sees.** Its 1 s dashboard cache made the dashboard lag a write by 300 to 700 ms, and it
  wrote at 0.58× on `:memory:`; A is out on both counts.

## Method

**What was built.** Five patches over `app/` at ddfff0f (the skeleton 6d37506 on the vendored fork), as M1 can take
them, in `S0.4/candidates/`:

| Patch | What it does |
|---|---|
| `v3/0001-store-v3.patch` | store v3 (D16, PLAN §11.1) from research 12's prototype: one writer connection under `wlock`; one read-only `OPEN_NOMUTEX` connection per event-loop thread, opened lazily through a `@(thread_local)`, with every table's read statements prepared on it; `SQLITE_DBCONFIG_ENABLE_QPSG` on every connection before any prepare; WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `journal_size_limit=64 MiB`; a write reads its row back on the writer under `wlock`. `MEMMODE` (env) serves `:memory:` as `ephemeral` (default: a WAL file `skel-mem-<pid>-<n>.db` in the temp dir, deleted on close; each boot sweeps the files of dead processes) or `single` (one in-RAM connection, reads under `wlock`). Tests: a reader thread sees the writer's commits on its own connection; 1000 pages with changing bound LIMIT/OFFSET re-prepare 0 times in both modes (§18.2's micro-guard) |
| `v3/0002-sort-indexes.patch` | migration `0004_sort_indexes.sql`: `(name, id)`, `(email, id)`, `(score, id)` and the role and status label-rank `CASE` expressions with `id` (named `idx_contacts_by_*`: 0001 already has an `idx_contacts_status`). A test runs `EXPLAIN QUERY PLAN` on all ten page statements and fails if one sorts in a temp B-tree |
| `A/0001-single-dashboard-cache.patch` | `MEMMODE=single` by default; `repo_contact_stats` reuses its aggregate for 1 s (test included) |
| `B/0001-ephemeral-unsynced-tmpfs.patch` | `synchronous=OFF` on the ephemeral file; on Linux the file goes to `/dev/shm` when it exists |
| `C/0001-group-commit.patch` | on top of B: `repository/writer.odin`, a writer thread. Create, edit, cycle and delete (`/contacts`, `/forms/submit`) are queued; the thread takes every write waiting (up to 100), runs them in one `BEGIN IMMEDIATE … COMMIT` with each read-back inside it, and posts the results to the loops that queued them, one `next_tick` per loop per batch; the handler answers from there. A write that fails alone (a constraint, a missing row) fails alone; a lost transaction fails the batch. Test: a seven-write batch answers each write as a lone write would |

The candidates, as `build.sh` assembles them: **v3** = v3/0001 + 0002 (and `v3noidx` = 0001 only, research 12's v3,
for comparison); **A** = v3 + A; **B** = v3 + B; **C** = v3 + B + C. On a file DB, B is v3 (its changes touch only the
ephemeral file), A adds the dashboard cache, and C adds group commit, which is X17's fallback for write@file.

**Build.** `S0.4/build.sh [--out DIR] [--test] [candidates]` copies `app/` to `DIR/base`, applies each candidate's
series to its own copy and builds `odin build src -o:speed -warnings-as-errors -define:VERSION=s04-<candidate>` (the
`x-version` header names the candidate). It runs in Git Bash (Windows binaries) and in WSL (Linux binaries). SQLite is
the skeleton's own build, as the baselines' is: on Windows the checkout's prepared `app/vendor/sqlite/sqlite3.lib`
(default flags, SHA-256 `d59c7173…2939`), on Linux `prepare.sh`'s `clang -O2` build of the same amalgamation (clang
18.1.3, `sqlite3.a` SHA-256 `82556775…ac64`). Toolchain: Odin dev-2026-10 (`84bc3fc`) on both legs, Windows 11
and Ubuntu (WSL2) on the dev PC (§18.5).

**How each mode runs.** Nothing else differs; `SEED=1` matters only for a file DB.

| Candidate | `:memory:` mode | Environment for the `:memory:` cells | File-DB cells |
|---|---|---|---|
| v3 | ephemeral | `DB_PATH` unset or `:memory:` | `DB_PATH=<file> SEED=1` |
| v3 (single + QPSG + indexes, without A's cache) | single | `MEMMODE=single` | — |
| A | single | `DB_PATH` unset or `:memory:` (`MEMMODE=single` is the default) | `DB_PATH=<file> SEED=1` |
| B | ephemeral, unsynced, `/dev/shm` on Linux | `DB_PATH` unset or `:memory:` | same as v3 |
| C | as B, writes group-committed | `DB_PATH` unset or `:memory:` | `DB_PATH=<file> SEED=1` |

With S0.1's driver: `VARIANTS="… v3=<dir>/v3 A=<dir>/A B=<dir>/B C=<dir>/C"`, `VSTORES_A=mem VSTORES_B=mem`, no
`VENV_*` needed (each binary's default is its mode); `v3s=<dir>/v3` with `VENV_v3s="MEMMODE=single" VSTORES_v3s=mem`
adds single without the cache.

**Measurement.** S0.1's loop and builds (`S0.1/parity.sh`, `analyze.mjs`), in the same rounds as HEAD and v1.1.1:
one run per leg of 3 rounds × 10 scenarios × {mem, file}, with A and B on the `:memory:` cells only; then the n = 5
re-run of every failing store cell (`pages`, `list`, `mixed`, with B, C and v3), and C again in S0.2's sweep rounds of
`static`, `seo` and `write` once the fork had F-7's sweep. The candidates were rebuilt with `build.sh` on the
measurement's checkout, so every binary in a round shares one fork and one SQLite library per leg.

**Checks.** `--test` runs `odin check src -vet -strict-style -warnings-as-errors`, `odin test src/repository` and
`odin test src/views` in every tree. `S0.4/check.sh BIN_DIR` starts each candidate in each of its modes (fresh server,
`LOG_LEVEL=warn`) and runs `S0.4/smoke.sh` against it: 42 curl checks of the list (sorted by name, name_desc,
email_desc and score across pages, paged, clamped, filtered), search and the JSON API, a create, an edit, a drawer edit,
a cycle and deletes answered with the stored row, 422 and 404, `/forms/submit`, the dashboard against `/data` right
after a write, and 40 concurrent creates and deletes that must each answer with their own row. `check.sh --k6` adds
one k6 round of every `load-tests/scenarios/*.js` per mode (200 VUs, `scale` at 20 VUs over 20k rows; 1 s warmup, 5 s
window; fresh server each) and asks `/healthz` after. On Linux the servers ran in WSL and k6 v2.0.0 ran on Windows,
through WSL's localhost forwarding (WSL has no k6). The e2e `api` and `chromium` projects ran against C and against
A, each from a scratch copy of `e2e/` whose `../app` was that candidate's tree (global-setup builds it there).

## Caveats

- **The k6 smoke above is not a measurement.** Its rounds are 5 s and unpaired; only the parity tables, from S0.1's
  interleaved rounds, are.
- **The candidates link the default-flags SQLite**, as the baselines do (§18.2 step 1). With it every `sqlite3_malloc`
  takes one global mutex (`MEMSTATUS=1`), which caps sorting across per-loop readers (research 12 §8: +26 % for v3 on
  `scale@20` with the tuned lib). M1's `skeleton` links S0.11's tuned lib, which favours C's 16 readers: its gate run
  may read `pages@mem` and `list@mem` higher than here, and the exceptions stay until a run passes without them.
- **The Linux leg's k6 ran inside WSL** for the parity rounds; the smoke above ran it on Windows through WSL's
  localhost forwarding, whose 0.6 s pickup lag a driver must wait out before `scale`'s setup (Results).
- **C's continuation had no generation check in the spike** (Decision): M1 builds it on F-13's deferred response
  (S0.5), and its drill is a connection cut while its write is queued: **UNVERIFIED (M1)**.
- **C was checked in its own mode only.** `MEMMODE=single` with C's writer thread builds and should work (the thread
  takes `wlock`, as single's reads do), but no check ran it.
- **What the patches leave for M1:** the guard's pulled reader reset (S0.6) and the per-loop tick that calls it; the
  query pool; keyset paging; the writer queue's metrics. The first read on each loop opens its reader (about 16 ms on
  Windows, under 1 ms on Linux, in the smoke's logs), which the gate's 3 s warmup absorbs.
- **Ephemeral files after a hard kill** are swept at the next boot: checked on both OSes (Results). On another Unix
  (macOS) the sweep leaves every file alone, since it has no `/proc` to tell a dead process from a live one.
