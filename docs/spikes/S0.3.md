# S0.3 htmx extensions in real browsers against Odin streams

**Closes:** hx-sse/ws/multipart never ran in a browser against Odin (digest critic) · **Pass criterion:** 03's 29
contract checks as Playwright specs against a `platform/stream` prototype on the fork: Chromium and WebKit pass;
Firefox in CI at M2
**Result:** PASS with a change: 29/29 on Chromium and WebKit against the Linux build, 28/29 against the Windows build
(#29, fan-out across loops, is the Linux leg's by design), and 20/20 browser checks of the three extensions in both
engines on both legs; the browsers forced two changes to the stream code, and a third, a fork change for WebSocket close
1013, is now in and passes · **Date:** 2026-10-26 · **Commit:** 15e3495 (the fork as of 3c07c77), then the 1013 runs on
the fork with `stream_end`'s deadline (committed with this record)

## Decision

PLAN §8.2 and §9 hold in Chromium and WebKit. Each extension swaps what the Odin server sends: hx-sse swaps unnamed
events (OOB into a live log) and turns named ones into DOM events; hx-ws sends form values as JSON and swaps HTML and
JSON envelopes; hx-multipart routes each part to its own target as soon as its `Content-Length` is in. Close codes
1011-1014 bring the socket back and 1008/1009 stop it. SSE resumes by `Last-Event-ID`, by the render-time `after` and
by `resync`, also across a restart; multipart resumes by `HX-Last-Part-ID`. The strict CSP (`connect-src` falling back
to `'self'`) admits the page's own `ws://` socket in both engines. PLAN.md and DECISIONS.md are not changed by this
spike; its three changes are folded into PLAN §8.2, §9.3, §9.4, D12 and D13:

1. **§8.2 and D12: a stream's first bytes go out with its headers.** WebKit resolves a streamed `fetch` only at the
   first body bytes. A quiet SSE stream stayed "connecting" until the loop's first heartbeat (19.5 s), and htmx's 60 s
   request timeout runs until the response resolves; a one-shot multipart whose first part took longer would be
   aborted. `sse_begin` now writes a comment line (`: open`) and `multipart_begin` a CRLF preamble, which the parser
   discards. Proposed text for §8.2, after the headers sentence: "Every stream also writes its first bytes with the
   headers (an SSE comment line, a multipart CRLF preamble): WebKit resolves a streamed fetch only at its first body
   bytes (S0.3)."
2. **§9.3 and D13: the epoch changes on every boot, even within a second.** With whole seconds, the restart spec
   stopped the server and started the next one on the same port within the same second; the old `Last-Event-ID` read
   as this epoch, and the page got a replay of the new process's ring instead of `resync`. The hub now uses boot time
   in milliseconds. Proposed text for §9.3, after "process-wide and monotonic": "The epoch is the boot time in
   milliseconds, so a restart inside the same second still starts a new epoch (S0.3)."
3. **§9.4, D13 and F-1: "WS closes 1013" for a slow consumer needed a fork change, now made.** The fork's
   `stream_write` ended a stream past its cap at once, with no last frame, so the client saw the socket drop (1006).
   F-1's `stream_end` now takes a deadline, and `stream_would_overflow` tells a protocol when the next write would pass
   the cap: `platform/stream` closes with 1013 there (keeping room for the close frame) and ends the stream with 2 s,
   after which a peer that hasn't read is cut off as `Too_Slow`. Both checks pass in both engines: a peer that reads
   again gets the close frame last (both legs, 3 of 3 runs each); a peer that never reads is cut at the deadline
   (Windows; from Windows the WSL leg can't make a peer that stops reading, because WSL's port relay keeps reading on
   its behalf, so that one check is skipped there).

Also from this spike: the `e2e/spikes/S0.3/` specs are the start of M2's realtime specs (§19.1.3); keep their
spec-per-plan-claim shape there.

## Method

- **Box:** the dev PC, Windows 11, and Ubuntu (WSL2) on kernel 6.18 on the same PC. Odin dev-2026-10 (`84bc3fc`) on
  both; Node 22.16; Playwright 1.63.0 with its Chromium and WebKit builds (WebKit is Playwright's Windows build).
  Firefox does not launch on this PC; the config lists it for CI.
- **Server** (`docs/spikes/S0.3/server/`), on the vendored fork (`app/vendor/odin-http`, F-1 streams, F-4 thread hooks):
  - `platform/stream`: the SSE encoder (CR, LF and CRLF each start a `data:` line), the WS handshake with its own
    `Origin == SITE_URL` check (no `Origin`: not a browser, passes) and version 13 → else 426, a strict RFC 6455
    codec (RSV, masking, control frames, UTF-8, close codes, 64 KiB cap; 1002/1007/1009), shutdown → 1012, and the
    multipart writer (random boundary, CRLF framing, `Content-Length` per part, one chunk per part); every stream sends
    `X-Accel-Buffering: no` and `Cache-Control: no-cache`.
  - `platform/hub`: 03's hub shaped to PLAN §9.2-9.3: publish from any thread, one inbox per loop registered from
    F-4's `on_thread_init`, at most one wakeup per loop per burst, a 256-message ring, ids `<epoch>-<seq>`, the
    connect procedure without the store step (Last-Event-ID, then `after`, else `event: resync` whose id moves the
    cursor to now), ring refs copied under the mutex and written after it, a Close message (a kick) that ends SSE and
    closes sockets with a code, a 20 s heartbeat per loop.
  - `main.odin`: 03's routes, `/events?t=…&after=…`, `/publish`, `/admin/close?t=…&code=…`, `/stats`, and four pages.
    4 loops.
- **Pages:** htmx 4.0.0 with hx-sse, hx-ws and hx-multipart, fetched by `docs/spikes/S0.3/prepare.sh` from the pinned
  unpkg URL and checked against 04 §1.3's SHA-256, embedded with `#load` as one bundle loaded with `defer`, the
  `htmx-config` allowlist `sse, ws, hx-multipart`, and the skeleton's CSP without its hash. As PLAN §9.1 says:
  `/p/live` has the layout stream (`<div id="live" hx-sse:connect="/events?…&after=<cursor>">`) feeding a
  `<div role="log">` by OOB, a fragment refetched on `resync from:body`, and an `hx-post` answered with a stream;
  `/p/chat` has one `hx-ws:connect` in the main region and an `hx-ws:send` form; `/p/mp` has a one-shot multipart
  request and an `hx-multipart:connect` feed; `/` has all three on one page.
- **Specs** (`e2e/spikes/S0.3/`): `contract.spec.ts` (03's 29, numbered as `test.mjs` runs them), `plan.spec.ts`
  (4 plan claims at the protocol level), `extensions.spec.ts` (20 browser checks; each also asserts no CSP violation
  and no uncaught page error). One worker, one server per worker; the restart spec starts its own two.
- **Commands**, from the repo root, then from `e2e/`:

  ```
  sh docs/spikes/S0.3/prepare.sh
  npx playwright test -c spikes/S0.3/playwright.config.ts --project=chromium --project=webkit
  ```

  `global-setup.ts` checks the pins and builds the Windows binary with `odin build docs/spikes/S0.3/server
  -collection:fork=app/vendor -out:docs/spikes/S0.3/server/bin/s03.exe -vet -strict-style -warnings-as-errors`. Linux
  leg: copy `app/vendor/odin-http` and `docs/spikes/S0.3/server` into the WSL filesystem with their relative paths,
  build there with the same command, and run the specs with `S03_LEG=wsl S03_WSL_BIN=<the binary>` (and
  `S03_WSL_DISTRO` for a distro that isn't the default). The fixture starts it through `wsl.exe` with `BIND_ALL=1` and
  reaches it at `127.0.0.1:<port>`.
- n = 3 runs per leg, each with both engines.

## Fork change

Made in F-1 (`app/vendor/odin-http/stream.odin`, listed in `UPSTREAM.md`), so `platform/stream` can close a slow socket
with 1013 and still cut a peer that never reads again. `platform/stream` closes with 1013 and a 2 s deadline when
`stream_would_overflow` says the next frame would pass `max_queued`; the hard cap in `stream_write` stays as the
backstop. The diff as proposed (the build adds `stream_would_overflow`):

```diff
-// Ends the stream once everything queued is sent. A chunked stream then serves the
-// connection's next request; a raw or close-delimited one closes it.
-stream_end :: proc(s: ^Stream) {
+// Ends the stream once everything queued is sent. A chunked stream then serves the
+// connection's next request; a raw or close-delimited one closes it. With a deadline, a peer
+// that hasn't taken the rest by then is cut off and the stream ends as Too_Slow.
+stream_end :: proc(s: ^Stream, deadline: time.Duration = 0) {
 	if s.done || s.ending { return }
 	if s.framed { append(&s.queue, "0\r\n\r\n") }
 	s.ending = true
 	if s.send_op == nil && len(s.queue) == 0 {
 		_stream_finish(s, .Ended)
-	} else {
-		_stream_kick(s)
+		return
+	}
+	_stream_kick(s)
+	if deadline > 0 && s.aux_op == nil {
+		s.aux_op = nbio.timeout_poly(deadline, s, proc(_: ^nbio.Operation, s: ^Stream) {
+			_stream_invoke(s, proc(s: ^Stream) {
+				s.aux_op = nil
+				_stream_finish(s, .Too_Slow)
+			})
+		})
 	}
 }
```

`stream_shutdown` already replaces `aux_op` with its own grace, so a drain still wins. After the change, the full suite
ran once more per leg: Windows 108 passed (54 per engine, #29 as its declared failure); Linux 106 passed and 2 skipped
(the never-reads check, as above). The slow-consumer spec publishes its 200 frames 50 at a time: one by one they took
about 10 s through WSL's relay, longer than the 2 s deadline, so the reader came back after the cut.

## Caveats

- Firefox did not run (CI at M2). WebKit is Playwright's Windows build: whether Safari and the Linux WebKit in CI hold
  a streamed response until its first bytes is **UNVERIFIED (M2 CI)**; the first bytes are harmless either way.
- Not exercised: a hidden tab (`pauseOnBackground`), hx-sse's retries after a 403 (**UNVERIFIED (M4)**, X19),
  `multipart/parallel`, the browser's 6-connection limit, HTTP/1.0 peers (F-2), proxies (S0.8; `e2e-proxy` at M2),
  hx-csp inside stream fragments (M2), and a fuzzer on the codec (Autobahn at M2).
- The hub is the minimum: one ring for all topics (the plan's is per topic), no TOPICS tables or perm checks, no
  keyset replay, no policies, no caps past the fork's per stream, no pong deadline, no guarded mutex. Stream state
  lives on the heap, not in a per-stream arena (D12's third bucket).
- A WS handshake without `Origin` passes, as the cross-site guard lets non-browser requests pass; PLAN §8.2 says only
  `Origin == SITE_URL`. M1 should say which (a device client such as `cmd/term-agent` sends none).
- The 1013 close is checked against this spike's `platform/stream`; M2's `wsdata` and back-pressure specs keep it.
- No performance claims: the box ran other agents' work.
