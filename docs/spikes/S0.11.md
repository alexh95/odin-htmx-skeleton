# S0.11 Tuned SQLite

**Closes:** S10 flags across OSes · **Pass criterion:** builds on Windows and Linux (macOS in CI at M1); size delta
≤ 230 KB; the skeleton's store tests pass
**Result:** PASS: the tuned lib builds on Windows (clang, MSVC) and Linux (clang, gcc), adds 192,904–228,584 B to the
skeleton, and the store and views tests and a running smoke pass on both · **Date:** 2026-10-26 · **Commit:** ddfff0f

## Decision

S10's flags stand as PLAN §11.2 and D16 list them. PLAN.md and DECISIONS.md are unchanged by this record. Proposed for
PLAN §11.2 (see Caveats for why):

- The `ENABLE_FTS5` row gains S0.11's numbers: +226,304 B on Windows (clang 19), +254,728 B on Linux (clang 18,
  unstripped), at ddfff0f.
- The `OMIT_LOAD_EXTENSION` row reads: "the Linux lib references no `dlopen`, so `platform/sqlite` drops
  `system:dl`; on glibc 2.34 and later the skeleton links without it with either lib."
- The section's last sentence becomes: "S0.11 built it on Windows (clang 19, MSVC 19.43) and Linux (clang 18, gcc 13):
  +192,904 to +228,584 B over the default flags; the store and views tests and a smoke pass on both. `prepare.{sh,bat}`
  hold the flags in one `SQLITE_FLAGS` string and rebuild the lib when it changes."

How `prepare.*` should compile the lib at M1. The flags live in one string, the same in both scripts. `cl` accepts
`-D` as well as `/D` (checked: the `-D` lib behaves the same), so one string serves `cl` and `clang`:

```
SQLITE_FLAGS=-DSQLITE_DQS=0 -DSQLITE_DEFAULT_FOREIGN_KEYS=1 -DSQLITE_THREADSAFE=2 -DSQLITE_DEFAULT_MEMSTATUS=0 -DSQLITE_OMIT_LOAD_EXTENSION -DSQLITE_OMIT_SHARED_CACHE -DSQLITE_ENABLE_FTS5
```

| OS | Command (in `vendor/sqlite/`) | Checked here |
|---|---|---|
| Windows, `cl` on PATH | `cl /nologo /c /O2 /MT %SQLITE_FLAGS% sqlite3.c` then `lib /nologo /OUT:sqlite3.lib sqlite3.obj` | yes (MSVC 19.43) |
| Windows, no `cl` | `clang -O2 -c -fms-runtime-lib=static %SQLITE_FLAGS% sqlite3.c -o sqlite3.obj` then `llvm-lib /nologo /out:sqlite3.lib sqlite3.obj` | yes (clang 19.1.0, from a shell without vcvars) |
| Linux | `"$CC" -O2 $SQLITE_FLAGS -c sqlite3.c -o sqlite3.o && ar rcs sqlite3.a sqlite3.o` (`CC` = clang, else gcc, as today) | yes (clang 18.1.3, gcc 13.3.0) |
| macOS | the Linux line, with Xcode's clang and ar | no: UNVERIFIED (M1 CI) |

- **Rebuild on a flag change.** Today both scripts skip the compile when the lib is newer than `sqlite3.c`
  (`prepare.sh:68`, `prepare.bat:31`), so an existing checkout keeps its default lib after the flags change. Write
  `SQLITE_FLAGS` to `vendor/sqlite/.flags` after each compile, and skip only when the lib is newer and `.flags` matches.
  CI's prepare cache already hashes `prepare.sh`, so it misses when the flags change there.
- **Windows without MSVC's cl.** `prepare.bat` falls back to clang + llvm-lib when `cl` is absent, and fails only when
  neither is on PATH. clang found the MSVC and SDK headers by itself.
- **The binding** (`platform/sqlite` at M1) drops `system:dl`.

## Method

- **Box:** the dev PC (Windows 11, 16 threads), busy with other agents; the Linux leg in WSL2 (Ubuntu), from copies in
  WSL's own filesystem. Odin `dev-2026-10-nightly:84bc3fc` on both.
- **Source:** the pinned amalgamation in `app/vendor/sqlite/` (3.53.4, `sqlite3.c` SHA-256 `b1dd5d74…8189`, the same
  file 12 §8 measured).
- **Libs:** `build-libs.sh` compiles three variants with clang `-O2`: `default` (no defines), `tuned` (the seven flags
  above) and `tuned_nofts` (all but `ENABLE_FTS5`). On Windows it adds `-fms-runtime-lib=static` and archives with
  `llvm-lib`; on Linux it uses `ar`, and `CC=gcc` repeats the set with gcc. `build-libs-cl.bat` builds `cl_default`
  and `cl_tuned` with `cl /O2 /MT`, as `prepare.bat` does today (MSVC 19.43, VS 2022 Build Tools).
- **Sizes:** `measure.sh` copies each lib over a scratch copy of `app/` (`vendor/sqlite/sqlite3.{lib,a}`) and runs
  `odin build src -o:speed`; n = 3 rounds per variant (gcc: n = 1).
- **Tests:** `odin test src/repository` and `odin test src/views` against each tuned lib (`TEST=<variant> measure.sh`).
- **Smoke:** `smoke.sh` starts the tuned build with `SEED=1` on a file DB and on `:memory:`, then checks `/healthz`, `/`
  and `/data`, the contacts fragment under all five sorts, a `POST /contacts`, `/search` and `/api/search` finding it,
  and a burst of 400 requests from 16 clients (half of them writes). Then `--backup` (`VACUUM INTO`) on the file DB.
- **Flag effects:** `traps.c`, linked against the default and the tuned lib, reads what each flag changes through the C
  API. `nm -u` lists the Linux libs' undefined `dl*` symbols. A copy of the binding without `system:dl` is linked
  against both Linux libs.

The skeleton against each flag:

- **`DQS=0`:** its SQL has no double-quoted literal. Every statement, the 10 sort variants included, is prepared at
  boot (`prepare_contacts`, `prepare_events`), and boot passed on both OSes.
- **`OMIT_SHARED_CACHE`:** nothing in `app/src` opens `cache=shared`. The trap holds: such a URI opens without error and
  gives a private, empty database.
- **`DEFAULT_MEMSTATUS=0`:** the skeleton does not bind `sqlite3_memory_used`. `sqlite3_db_status` still reports, so
  store v3's obs numbers (D16) work.
- **`THREADSAFE=2`:** the skeleton shares one connection across its 16 server threads, always under its `RW_Mutex`
  taken exclusively (`db.odin`), which multi-thread mode allows. The 16-client burst passed on both OSes.
- **`DEFAULT_FOREIGN_KEYS=1`:** the skeleton sets the pragma anyway; nothing changes for it.

## Caveats

- **Linux clang's margin is thin:** +228,584 B is 1,416 B under 230,000 B (6,936 B under 230 KiB). Unstripped Linux
  binaries carry FTS5's symbol names; stripped, the delta is +216,944 B. The production image compiles with Debian
  trixie's clang, not clang 18; its delta is UNVERIFIED (M1, the docker job). §18.4's 2.75 MB budget is a Windows
  figure: the tuned Windows skeleton is 2,658,304 B (clang) or 2,595,328 B (MSVC); on Linux it is 2,774,760 B.
- **Exact sizes move by tens of bytes with the build directory**, since Odin embeds source paths; deltas within one copy
  don't. S0.9's Linux default build at the same commit read 2,546,152 B.
- **The default Windows lib today** is the one `prepare.bat` left in the checkout, built earlier by a `cl` this record
  did not identify; the skeleton against it is 2,412,544 B. The table compares each compiler with itself.
- **One Linux build failed spuriously:** in round 1, `tuned_nofts` stopped with "'context' has not been defined within
  this scope" at `vendor/odin-http/response.odin:143`, on source that built before and after (1 of 15 Linux builds;
  0 of 16 on Windows). It looks like a checker flake in Odin dev-2026-10, unrelated to SQLite. Its cause is UNVERIFIED;
  CI at M1 shows whether it recurs.
- **macOS is UNVERIFIED** (M1 CI). So is linux_arm64 (09 §6.4).
- **`THREADSAFE=2` relies on the locking discipline.** A future path that touches a connection outside its lock races
  silently where `THREADSAFE=1` would have serialised it. No TSan run here. M2's TSan gate names hub, stream and
  workers, not `store/sqlite`, so store v3's connections first meet TSan at the slice gate (d) in M4: UNVERIFIED until
  then. Proposed: add `store/sqlite` to M2's TSan list.
- **`DEFAULT_FOREIGN_KEYS=1` and migrations:** a migration that rebuilds a table (the 12-step `ALTER TABLE` procedure)
  must turn foreign keys off itself, outside its transaction. D16 keeps migrations additive, so none does yet.
- **Speed was not re-measured;** 12 §8's numbers stand.
