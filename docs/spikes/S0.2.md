# S0.2 The fork under the skeleton's k6

**Closes:** "a forked odin-http keeps the request-path throughput" (03 §10.4) · **Pass criterion:** 709bc94 rebuilt on the
fork with F-1 and F-5…F-12: paired ratio ≥ 0.97 against HEAD on every scenario, both legs
**Result:** PASS with a change: on the fork as first built, F-7's per-read timeouts cost 2–4 % on the lightest route
(seo on a file DB at 0.95 of HEAD on Linux); F-7 now enforces its deadlines with a 1 s sweep per thread, and with that
every cell is at parity with HEAD on Linux (0.98–1.04, n = 5), and on Windows every median reads 0.97–1.00, its few
misses single rounds or p99s that move between runs · **Date:** 2026-10-26 · **Commit:** 575f5c7 (the sweep);
the first rounds ran on 196b646 (F-1, F-2, F-4..F-13 with per-read timeouts)

## Decision

The fork keeps the request path's throughput, after one change to F-7, now in `app/vendor/odin-http` (575f5c7) and its
`UPSTREAM.md`, PLAN §8.1 and D11: **the idle, header and body deadlines are enforced by one 1 s timer per thread that
walks its connections, not by a timeout on every read.** On io_uring a per-read timeout is a linked operation, an extra
submission and completion per request; on the lightest route (`seo`, about 64k requests per second on 16 loops) it cost
2–4 %, and the build with the timeouts off was the only one that passed every cell. A deadline now fires up to a second
late, which the 10, 30 and 75 s timeouts don't notice. The sweep also exposed a gap present upstream: `_body_length`
marks the body read before scanning it, so a body cut off part way kept its connection alive after the 400 with the rest
unread on the wire; a body-phase timeout now closes the connection (S0.7's timeouts phase checks all three deadlines).

The guard (F-5's `invoke`, the crash guard of S0.6) costs nothing measurable here: the fork with and without it read the
same within the noise on every cell, on both legs.

Measured as the criterion says, against HEAD alone: the fork builds keep HEAD's store, so v1.1.1's faster lists say
nothing about the fork. (The parity gate proper compares the starter's `skeleton` with max(HEAD, v1.1.1) on store
routes and HEAD alone on the light routes, Q35; S0.1.)

## Method

- **Builds** (`tools/baseline/baseline.sh`): HEAD = v1.2.0 (709bc94) on laytan/odin-http fac113f; **fork** = 709bc94 on
  the vendored fork with the crash guard installed as F-5's `invoke` hook (`--fork --guard`), as M1's profiles will run;
  **fork_noguard** = the fork without the guard (`--fork`); **fork_notimeout** = the fork and guard with F-7's three
  timeouts set to 0 (`--no-timeouts`). Every build links the same SQLite library per leg, `-o:speed`, Odin dev-2026-10.
  v1.1.1 runs alongside as S0.1's second baseline.
- **Loop:** S0.1's (`docs/spikes/S0.1/parity.sh`, `analyze.mjs --against head`): fresh server per run, `THREADS=16`,
  `LOG_LEVEL=warn`, k6 v2.0.0 at 200 VUs, 3 s warmup + 10 s window, variants back to back per cell with the order
  rotated each round, the host's CPU sampled per block.
- **Runs:** first, all 10 scenarios × {mem, file}, n = 3, both legs (with S0.1 and S0.4's builds); then the failing
  cells' 5-round re-run (§18.2) of `static`, `seo` and `write` with fork, fork_noguard and fork_notimeout; then the same
  three scenarios, n = 5, with the sweep build (Windows `seo` and `write` again, and Linux `static@file`, once the box was
  quiet).
- **Box:** the dev PC, Windows 11 native and Ubuntu (WSL2), as S0.1.

## Caveats

- The Windows leg's noise (bands 1.05–1.58 on the lightest cells) is wider than the effect measured here; the Linux leg
  decides, as §18.5 says for 3 % effects.
- The fork builds here are 709bc94's app on the fork, as the criterion asks, not M1's `cmd/skeleton`; the gate measures
  that at the M1 exit.
- F-7's sweep makes a deadline fire up to `SWEEP_INTERVAL` (1 s) late, and the close delay adds 500 ms before the peer
  sees the close; S0.7's timeouts phase allows for both.
