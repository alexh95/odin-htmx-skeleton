## Decision

The reference stands as §18.1 defines it, measured: HEAD (709bc94, v1.2.0) and v1.1.1, both legs, n = 3, with the
noise bands below. Two things change in how the gate reads it.

1. **v1.1.1 is the faster baseline on 16 of 20 cells on each leg**; HEAD wins `scale` (1.28–1.40×) and ties `write`
   on a file DB. That was the design's expectation (§18.1): HEAD's store routes are 2.5–4× slower.
2. **On the lightest routes v1.1.1 is faster for a reason the starter can't copy.** `static`, `seo` and `write` on
   `:memory:` run 4–8 % faster on v1.1.1 on both legs (HEAD / v1.1.1 = 0.92–0.96). Those routes barely touch the store:
   the difference is 1.2.0's per-request work (security headers and the strict CSP, the cross-site write check, body
   caps and 422s). The plan keeps all of it and adds more (§17). Under "C / max(A, B) ≥ 0.97" a starter that is exactly
   as fast as HEAD fails those cells, and so does HEAD itself (median 0.92–0.95 against max(HEAD, v1.1.1) on `static`
   and `seo`). That was Alex's call (D38: nothing is waived without him), and he answered it on 2026-10-26 (**Q35**,
   ANSWERS round 5): **the light routes, `static` and `seo`, gate against HEAD 709bc94 alone; the store routes keep
   max(HEAD, v1.1.1)**. Folded into PLAN §18.2's pass rule, D38 and Appendix C. `write` on `:memory:` is a store route,
   so it keeps max(A, B), and a `:memory:` cell the chosen mode fails is Q6's case (S0.4).

The Linux noise band is tight (1.00–1.05 per cell, max/min over 3 rounds), so the Linux leg settles 3 % effects; the
Windows leg's is 1.01–1.25 on undisturbed blocks and worse on disturbed ones, so a Windows-only miss within its band
is re-run (§18.2's rule) and read against Linux.

## Method

- **Builds:** `tools/baseline/baseline.sh v1.2.0 <out>` and `… v1.1.1 <out>`: `git archive` of each tag's `app/`,
  laytan/odin-http fac113f (both tags pin it), this checkout's htmx 4.0.0 and SQLite 3.53.4 library (both tags pin the
  same SHA-256s; the script checks), `odin build src -o:speed`, Odin dev-2026-10. Windows links prepare's `cl /O2 /MT`
  library; Linux prepare's `clang -O2` one. Every build in the run (S0.2's and S0.4's too) links the same library per
  leg.
- **Loop:** `docs/spikes/S0.1/parity.sh` (M1 folds it into `load-tests/run.sh --parity`): per round, per scenario, per
  store, every variant back to back on a fresh server, the order rotated each round; `THREADS=16`, `LOG_LEVEL=warn`,
  `SEED=1`; k6 v2.0.0 at 200 VUs (`scale`: 20 VUs over 20k rows), 3 s warmup + 10 s window; the skeleton's 10 scenarios
  from `load-tests/scenarios/`; the host's CPU sampled before each block (in WSL through `typeperf.exe`, since the VM
  can't see the host). `docs/spikes/S0.1/analyze.mjs` applies the pass rule and prints these tables (`--baselines`).
- **Box:** the dev PC (Ryzen 7 5800X, 8 cores and 16 threads, 64 GB), Windows 11 native, and Ubuntu (WSL2) with the
  server, k6 and the file DBs in WSL's own filesystem. Nothing else of this session ran during the rounds; other
  sessions' Docker stacks stayed up in WSL (a few game servers, under 5 % of a core).
- **Runs:** one run per leg of 3 rounds × 10 scenarios × {mem, file} with seven builds (these two plus S0.2's and
  S0.4's), 360 runs per leg; then 5-round re-runs of the cells that failed (S0.2, S0.4). Windows had six blocks over
  20 % host CPU (23–91 %), all inside cells the re-runs repeat; Linux had none over 13 %.

`scale` stays at 20 VUs in the gate (§18.2): at 200 it measures queueing, and the two baselines' order is the same as at
20 (HEAD 1.6–1.7× v1.1.1).

## Caveats

- Absolute numbers are this box's on this day: the gate compares only builds run back to back (§18.5).
- `write` on `:memory:` counts as a light route in item 2: HEAD and v1.1.1 run the same insert and their difference
  (6 %) matches `static`'s and `seo`'s; on a file DB the commit dominates and the two tie.
- v1.1.1 has no `LOG_LEVEL` (it logs nothing per request); HEAD runs with `LOG_LEVEL=warn` as §18.2 says, so the
  access log isn't part of item 2's difference.
- macOS isn't a leg (§18.5).
- Taking max(A, B) per round, as D38 says, favours the baseline slightly where A and B are close (the larger of two
  noisy samples), by about the noise band. With the light routes against HEAD alone, the one store cell where the two
  baselines tie is `write@file`, where the chosen candidate writes at 2.9–4.3×, so the rule stays as written; a gate
  run with a candidate inside the noise of a tied cell would read the ratio against each baseline separately.
