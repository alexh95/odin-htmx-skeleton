# S0.6 The guard in the fork + watchdog

**Closes:** 13 verified the pieces, not the integration · **Pass criterion:** the 15 crash kinds plus `sqlite` via
`TEST_ROUTES` on Windows and Linux; pure → 500 + 20/20 bystanders; lock, async, sqlite → exit 70 ≤ 6 s; WAL size flat
after 1000 pure traps mid-iteration (the reader-statement reset); 10k malformed requests including CL −5 → 0 deaths; the
watchdog exits ≤ 11 s on a 15 s block
**Result:** PASS with a change: 22/22 checks on Windows and 22/22 on Linux, once the reader reset is also pulled on each
loop's 1 s tick · **Date:** 2026-10-26 · **Commit:** 3c07c77 (the fork with S0.7's two F-9 refinements; the runs before them were on ddfff0f)

## Decision

D15's design holds as built: the guard sits in the fork's F-5 `invoke` hook, so it covers crashes inside odin-http's
own callbacks, the handler dispatch and stream callbacks, not just the app's handlers. The classification by counters
works on both OSes: 13 pure kinds recover with every bystander served, and a held lock, a posted op or a trap inside
SQLite exits 70 within about a second.

**One change, to PLAN §10.2 rule 3 and §11.1 (and D15):** the pulled reset of a loop's reader must also run on that
loop's 1 s tick, not only before the reader's next use. The first WAL run failed: on Windows the 1000 crashes landed on
one loop and every later read on another, so the crashed loop's reader was never used again and kept its snapshot,
and the WAL grew 165 MB in 5 s of writes. With the check also on the loop tick (the per-loop timer F-4 already gives the
watchdog), the WAL stopped growing. `guard` still never calls SQLite, and no new hook is needed: at M1,
`platform/store/sqlite` arms the 1 s timer itself, on a loop, the first time that loop's reader is used, and stops
re-arming it once the server drains (here the harness ran the check from its own loop tick). Folded into PLAN §5.1,
§5.2's table, §10.2 rule 3, D15 rule 3 and LEAN-COMPOSITION §5.

Also confirmed, and worth stating in §10.2: the burst rule works (the 101st pure recovery inside a minute exits 70),
and a crash line is written for every crash.

## Method

- **Server:** `S0.6/guardlab/`, a small server on the vendored fork (`app/vendor/odin-http` at the commit above) with
  `S0.6/guardlab/guard/` (the prototype of `platform/guard`) as its `invoke` hook and `on_thread_init` /
  `on_thread_shutdown` (F-4). The guard is a `setjmp` frame in `invoke`, `context.assertion_failure_proc` jumping back
  to it, and trap handlers: `sigaction` on an alternate stack per thread on Linux (glibc `_setjmp`, `SA_NODEFER`), a
  vectored exception handler and `_resetstkoflw` on Windows. Counters: `locks_held` (its `Mutex`), `async_posted`
  (`posted()`), `in_sqlite` (around every call in its SQLite binding, `S0.6/guardlab/sq/`). The store is store v3's
  shape: a WAL file DB, one writer connection behind the guard's mutex, one read-only connection per loop. A watchdog
  thread checks each loop's 1 s heartbeat (10 s stall) and the write lock (5 s); a dirty crash or a stall writes
  `last-crash.txt` and exits 70, and a dirty crash drains first, with a hard exit at 5.5 s in case a loop is wedged on
  the abandoned lock.
- **Crash routes** (`/crash/<kind>`, what M1 puts behind `-define:TEST_ROUTES`): assert, panic, ensure, bounds, slice,
  enum_index, type_assert, int_div_zero, int_mod_zero, nil_deref, nil_write, stack_overflow and stack_overflow_again
  (pure); lock and rwlock (a lock held), async (an op posted, then a panic), sqlite (a trap inside a SQL function, so
  inside `sqlite3_step`); `iter` (a pure crash between two steps of a reader statement); `block?s=15` (the loop sleeps).
- **Driver:** `S0.6/drive.mjs` (Node 22), a fresh server per case, 4 loops (`THREADS=4`), `-o:speed`, Windows 11
  native and Linux on WSL2 (the server in WSL, the driver on Windows over WSL's loopback forwarding).
  - pure: the crash and 20 bystanders (`/ui/ping` and a reader query) at once, each on its own connection;
  - dirty: the crash with 5 reader requests in flight, time to exit;
  - wal: 1000 `iter` crashes while writes go on, one read per loop, then 5 s of writes only, with the reset and
    without it (`NO_RESET=1`); the burst limit is raised to 5000 for this run only (`GUARD_BURST`);
  - malformed: 10,000 raw requests, 50 at a time, cycling 22 shapes: Content-Length `-5`, `9223372036854775808`,
    `18446744073709551617`, `+5`, `1_0`, `0x5`, `5, 5`; `OPTIONS *` and `Expect: 100-continue` with `-5`; chunked
    sizes `-5` and 18 hex digits; an unknown transfer coding; no Host; HTTP/2.0; a 9 KB request line and header; an
    unknown method; a bad header line; bare CRLFs; binary junk; a dot-dot path; half a body;
  - watchdog: one request that sleeps 15 s on its loop.

## Caveats

- The guard is formally undefined behaviour (Odin doesn't mark `setjmp` returns_twice, R4); it held here at
  `-o:speed` on both OSes, and the per-push crash drills (§19.1.10) are what keep it true across compiler bumps.
- The crash line carries the source location only for assert and panic; a trap (bounds, divide, fault) has the kind
  and code. The `core:debug/trace` capture and the split debug file of §10.2 rule 8 are M1 work.
- `rwlock` is counted by hand here (a plain `sync.RW_Mutex` plus a counted lock), standing for M1's rule that only the
  guard's mutex is allowed (`tools/check locks`).
- Throughput with the guard installed is S0.2's question, not this spike's.
- Windows put the crash and the reads on different loops in one run and on the same loop in others: which loop
  accepts a connection there isn't stable, which is why the tick-side reset is needed even on one box.
