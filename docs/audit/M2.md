# M2 audit: streams, the hub, and the features on them

An independent audit of milestone M2 (PLAN §19.2), by an agent that did not write the code. It applies the review
rubric (§19.2.2), the severity scale (§19.2.3) and the crash-zone rules of D15, and reads the vendored odin-http
diff line by line (D11).

**Method.** Read-only. A performance measurement may have been running on the same machine, so nothing was built,
checked, tested or run: no `odin build/check/test`, no server, no node, no k6, no Playwright, no drills. Every
finding comes from reading the source at `db27254` (HEAD's committed state; the working tree's uncommitted edits by
other sessions were not read). Where reading could not settle a point the finding says "suspected" and names what
would confirm it. Where a finding rests on the toolchain's own code (core:encoding/json, core:encoding/base64,
core:net's `percent_decode`, core:nbio's `send`, core:thread's stack size), that code was read at the pinned Odin.
Line numbers are at `db27254`.

**Result.** 0 CRITICAL, 2 HIGH, 9 MEDIUM, 5 LOW, 5 NIT. M2 cannot exit until M2-01 and M2-02 are fixed (§19.2.1:
exit needs 0 open CRITICAL or HIGH). M2-02 is rated HIGH under this audit's brief (data lost in normal use), not as a
crash. Of the six M1 findings M2 says it fixed (M1-02, M1-03, M1-04, M1-05, M1-07, M1-26), the code bears out all
six; M1-04's fix has two gaps, filed as M2-12.

### M2-01 · HIGH · nested JSON in a WebSocket frame overflows a loop's stack

**Where.** Two socket handlers pass a client's text frame, up to `WS_MAX_MESSAGE` (64 KiB,
`platform/stream/ws.odin:19`), to `json.unmarshal`: the lab's room, `features/lab/web/web.odin:236`
(`/lab/ws/chat`, `.Public`, on a host where no identity runs), and chat's socket,
`features/chat/transport_ws/ws.odin:83` (`.Chat_Read`). core:encoding/json has no depth limit. `unmarshal_any` first
runs `is_valid`, whose `validate_value` → `validate_array`/`validate_object` → `validate_value` recursion goes as
deep as the input nests; then `unmarshal_object` skips a field the struct lacks (hx-ws sends `{message, headers}`)
with `parse_value` → `parse_array` → `parse_value`, again a level per bracket, each frame holding a `Value`, an
`Array` and a `Source_Code_Location`. The frame is parsed in `_stream_feed` (`vendor/odin-http/stream.odin:365-374`)
on a loop thread, whose stack is core:thread's default: 1 MiB on Windows, RLIMIT_STACK (8 MiB typically) on Linux.

**Scenario.** One text frame: `{"message":"x","headers":` + 32,000 `[` + 32,000 `]` + `}`, or 65,000 `[` with no
close. That is 32,000 to 65,000 levels at about two frames each, 64,000 to 130,000 frames. Windows' 1 MiB leaves
8 to 16 bytes a frame, less than any x64 call takes (the return address and 32 bytes of shadow space): it overflows
for certain, as M1-17's 12,000 chunks did. On Linux the parse path needs about 256 bytes a level to pass 8 MiB,
which its frames very likely exceed: suspected; confirm with that one frame to `/lab/ws/chat` on a Linux `-o:speed`
build. The guard recovers a stack overflow as pure (M1-17: `kind=stack_overflow zone=pure`) and the socket closes
1011, but each recovery counts toward GUARD_BURST: past 100 in 60 s the next one is dirty, and the process drains and
exits 70.
Admission lets one address open 20 sockets a calendar minute (`STREAM_CONNECTS`), so one address reaches 40 within a
60 s window and three reach the burst. An IPv6 /64, or a few devices on a LAN, is enough. `/lab/ws/chat` needs no
identity, so on a public lab host unauthenticated clients can stop the process, again after every restart. If the
guard can't recover an overflow on some loop thread (the `sigaltstack` result is unchecked, M1-16), one frame is
CRITICAL. Rubric 7: the codec has fuzzing (Autobahn); the JSON behind it has none.

**Fix.** Never hand a frame to core:encoding/json unbounded: before `unmarshal`, a byte scan that refuses nesting
deeper than, say, 16 outside strings (a dozen lines in `platform/stream`, one definition for both callers), or read
the two fields hx-ws sends by hand. Add the payload to the drills beside `wsdata`, and a fuzz case.

### M2-02 · HIGH · the hub drops a live message when two publishers race

**Where.** `platform/hub/hub.odin:250-283`: `post` takes the hub sequence and puts the message in its ring under
`h.mu`, releases it (`:266`), frees what the ring evicted (`:268`), and only then appends the message to each inbox,
one inbox lock at a time, posting a wakeup per inbox (`:274-282`). `deliver` (`:351-352`) skips any message at or
below the subscriber's `last` and raises `last` to each message it writes. `last` exists to drop the copies a
subscription already replayed (`events.odin:115-117`), but this also assumes an inbox receives messages in sequence
order, which nothing guarantees once two threads publish.

**Scenario.** Bob posts in room 1 from loop 2 (seq 100, `chat.room:1`) while Carol types from loop 3 (seq 101,
`chat.typing:1`), or the scheduler's presence sweep or ops' 1 Hz job publishes. Bob's thread releases `h.mu`, frees
the message his post evicted from the room's full ring, and posts its first wakeup (a syscall); Carol's append
reaches loop 0's inbox first. Alice's `#live` on loop 0 is subscribed to both topics: the drain writes 101
(`last = 101`) and skips 100. Her page never shows Bob's message, and her `Last-Event-ID` is 101, so a reconnect
replays after 101 and doesn't bring it back either; only a reload does. The same race on one topic (two posts to a
room from two loops) drops the lower one for every socket and multipart subscriber whose inbox got them out of order.
A drain that runs between the two appends gives the same drop across two drains. No error, no counter, no resync. The
message is stored; the live view loses it for good, in normal use, under any concurrency.

**Fix.** Append to the inboxes while holding `h.mu`, right after the sequence is taken (each inbox lock nests inside
it; the drain takes only its own), and post the wakeups after releasing it: every inbox then receives in sequence
order. Independently, `last` need only stop the replay's duplicates: keep it at the subscription's snapshot instead
of advancing it per message (a live copy can't be delivered twice). A unit test with two publisher threads and one
subscriber of both topics, asserting no gap.

### M2-03 · MEDIUM · a stream's first writes can pass its queue cap, and then it never resumes

**Where.** A stream's queue is capped at `STREAM_MAX_QUEUED` (256 KiB; `platform/stream/limits.odin:50`, enforced by
the fork's `stream_write`, `vendor/odin-http/stream.odin:171-174`), and everything written before the first send
completes counts against it. Three handlers write a backlog at once: `/events`' ring and keyset replays
(`platform/hub/events.odin:131-134`, `:146-148`; a ring holds up to 256 messages and `HUB_RING_BYTES`, 1 MiB);
chat's socket, which sends the room's last 50 messages as one frame (`features/chat/transport_ws/ws.odin:64-69`) that
`ws_write_frame` refuses with 1013 once it would pass the cap (`platform/stream/ws.odin:134-141`); and chat's
multipart feed, which sends everything after `HX-Last-Part-ID` as one part (`transport_multipart/multipart.odin:44-50`).

**Scenario.** A chat message is up to 2,000 runes, and `esc` writes `&`, `"` and `'` as five bytes, so one message
renders to about 10.6 KB (all emoji, 8.6 KB). A member posts 25 messages of 2,000 `&`, under a minute at 5 per 10 s.
From then on every WebSocket connect to that room builds a ~265 KB snapshot frame and is closed 1013; hx-ws reconnects
on 1013, gets the same, and ends at admission's 429. WebSocket is the default transport (`CHAT_TRANSPORT=ws`), so the
room is unusable for everyone until enough short messages, posted over another transport, push the long ones out of
the last 50. Without malice the same holds for `#live`: a page that missed more than ~256 KiB of a room's ring (a
background tab through a busy hour) is closed `Too_Slow` on every reconnect, its `Last-Event-ID` never moves, and it
stops receiving anything (the Inbox and presence with it) until a reload. Multipart reconnects with the same
`HX-Last-Part-ID`, the same way.

**Fix.** A backlog must not trip the cap meant for a slow consumer: cap what a replay writes by bytes, well under the
queue cap, and answer the rest with `resync`; send a snapshot a message per frame (or part), newest first, up to a
byte budget; or give a stream's first writes their own allowance. Specs: a 300 KB ring replay, and a room with 25
long messages over WebSocket and multipart.

### M2-04 · MEDIUM · a ring made again after the idle sweep vouches for any cursor

**Where.** The idle sweep (`platform/hub/ring.odin:50-65`, run from `hub.odin:263`) frees a ring after `RING_TTL`
(10 min) and raises `h.floor`, so a cursor below the floor on a topic with no ring is resynced (`events.odin:102`).
But the next publish to that topic makes a new ring (`ring_for`, `ring.odin:37-45`) with `dropped = 0`, and
`ring_covers` (`:99-101`) then accepts any cursor from this epoch.

**Scenario.** Room 1 gets seq 100 to 110; Alice's tab was hidden at 105 (hx-sse closes a hidden tab's stream, D14).
The room is quiet for 10 minutes, 1,024 publishes elsewhere run the sweep, then a message arrives at seq 2000.
Alice's tab returns with `Last-Event-ID: <epoch>-105`: the new ring covers it, the replay is 2000 alone, and 106 to
110 are silently missing, with her cursor already past them. Without the new message she would have got `resync`.

**Fix.** Start a new ring with `dropped = h.floor` (conservative: nothing older than a sweep is vouched for), or keep
each swept topic's newest seq for the ring that replaces it. A case in `hub_test.odin`: sweep, publish, resume from
before the sweep.

### M2-05 · MEDIUM · presence keeps a map for every room id a member names

**Where.** `chat.presence` has a perm and no `allow` (`features/chat/web/web.odin:62`), so `/events` lets any member
subscribe to `chat.presence:<digits>`, and `watch_room` (`:445-453`) takes any `parse_id` key to `chat.join`
(`chat/chat.odin:306-319`), which makes `st.here[room]` (`room_presence`, `:369-373`) and publishes a change, which
makes a hub ring for that topic. `sweep_presence` (`:333-356`) deletes members who have gone, never a room's map, and
walks every room under `st.mu` (the lock each post's mention lookup takes) every 5 s, with a temp array per room.

**Scenario.** A LAN client with a nickname opens `/events?t=chat.presence:1,…,chat.presence:8`, lets it close, and
repeats with the next eight ids: at 20 connects a minute per address, 160 new room maps a minute, each kept for the
life of the process, plus a ring each until the idle sweep. A day from one address is ~230,000 maps, and the 5 s sweep
grows with them.

**Fix.** Give `chat.presence` and `chat.typing` an `allow` that checks the room exists, and delete a room's map in
the sweep once it is empty.

### M2-06 · MEDIUM · the memory stores keep every nickname's state, with eager rings and no cap

**Where.** `stores/memory/bot/store.odin:64-82`: each `POST /bot/c` (`features/bot/web/web.odin:36`, no rate limit)
makes a conversation whose turn ring is allocated whole, 200 × 80 B = 16 KB (`mem_store.ring_init`,
`platform/store/memory/memory.odin:44-46`); a member keeps 50, and `s.owners`, keyed by member id, never shrinks.
`stores/memory/notify/store.odin:50-57`: a member's first notification allocates a 200-item ring (16 KB), kept for
good. A nickname costs one `POST /login` from the LAN.

**Scenario.** A LAN client loops: `POST /login` (a new nickname, so a new id), then 50 × `POST /bot/c`. Each round is
51 cheap requests and 800 KB that never comes back: about 1,300 rounds to a gigabyte. Mentions do the same to notify,
16 KB per member mentioned.

**Fix.** Grow a ring as it fills (a dynamic array with the cap as its limit), rate-limit `POST /bot/c` with the asks,
and bound the members a memory store keeps (forget the least recently active past a cap, as chat's name map does).

### M2-07 · MEDIUM · the lab's publish endpoint lets anyone fill the hub's rings

**Where.** `features/lab/web/web.odin:125-148`: `POST /lab/publish` is `.Public`, has no rate limit, takes any
`[a-z0-9-]{1,40}` key and up to 60,000 bytes of text. Every publish lands in its topic's ring
(`platform/hub/hub.odin:255-264`), made on the topic's first publish, up to 256 messages and 1 MiB each. Nothing
bounds the rings in total; a ring goes only after 10 idle minutes, and only when a sweep runs (every 1,024 publishes).

**Scenario.** Unauthenticated POSTs to `?t=lab.feed:k1`, `k2`, … with 60 KB of text each: every key holds up to
1 MiB for at least 10 minutes. At 100 MB/s of upload that is 6 GB held a minute, and the process is OOM-killed long
before the first ring expires.

**Fix.** Rate-limit `/lab/publish` and `/lab/close` per client (`web.Limit`), and give the hub a total budget for its
rings: past it, evict the least recently published ring (raising `floor`, as the sweep does) or refuse new topics.

### M2-08 · MEDIUM · one chat message costs a store scan and a publish per reader

**Where.** `features/chat/web/web.odin:288-293`: after every post, `announce` sends each reader's unread count to
`notify.user:<id>`, counting it with `chat.unread` → `count_after` under the store's lock. Readers are whoever has
POSTed `/chat/r/<slug>/read` (no rate limit), up to `MAX_MEMBERS` (4,096) a room (`chat/chat.odin:248-261`), never
pruned.

**Scenario.** 4,096 nicknames each send one read receipt to a room. From then on every message there costs, on the
poster's loop, 4,096 scans of the room's ring and 4,096 hub publishes, each a heap message and a ring for that
member's topic (up to 256 messages). Five posts in 10 s is 20,000 publishes from one member; the 4,096 rings hold up
to ~250 MB until they idle out.

**Fix.** Publish counts only to readers with a stream open (presence knows), as one `.Latest` per member keyed by
room, or cap readers per room far below 4,096; compute the count once per post, not per reader.

### M2-09 · MEDIUM · F-17 frees a POST stream's request body while its handler still reads it

**Where.** `vendor/odin-http/stream.odin:145-149`: `stream_begin` deletes the scanner's buffer when nothing is
pipelined. A Content-Length body is a slice of that buffer (`_body_length`'s scan, `body.odin:148-154`), which front
keeps as `c.body` without copying. `web.form` decodes each field into the request arena, except a field whose
percent-encoding is malformed and has no `+`: `form_decode` returns it as the body's own slice
(`platform/web/respond.odin:196-204`). The bot's `ask` takes `q` from the form (`features/bot/web/web.odin:239-240`)
before `sse_begin`/`multipart_begin` (`:271-275`) and reads it after (`:280-287`: `title_of`, `keep`, `shell`,
`bot.request`). `POST /bot/ask` is `.Bot_Use`, guests included.

**Scenario.** A guest posts `q=hello%zz` (no `+`): `q` points into the scanner buffer, which `stream_begin` frees, and
`shell(q)` copies freed heap memory into the answer's first event. For a member, `keep`'s `store.new_op` can take the
same chunk, so the clone copies the op's own header bytes (heap pointers) in as the stored question, shown on the
conversation page. With a body near `ASK_CAP` the buffer grows to 128 KiB, which glibc maps with mmap; the free
unmaps it and the read faults, a pure crash (suspected: it depends on glibc's dynamic mmap threshold; ASan reports the
use after free on the first such request).

**Fix.** Copy the body into the request arena in front (one clone per request with a body), or have `stream_begin`
keep the scanner buffer when the request had a body; and have `form_decode` return a copy, or "", when decoding fails.

### M2-10 · MEDIUM · a handler's read transaction outlives a crash: stale reads and a pinned WAL

**Where.** `platform/store/sqlite/sqlite.odin:187`: a handler's first read begins a transaction on the loop's
reader; `handler_ended` (`:200-203`) commits it and `handler_began` (`:194-197`) rolls back one left open. A pure crash
in a handler skips `handler_ended` (front's `call`, `platform/app/front.odin:146-153`), so `tl_txn` stays set and
`tl_in_handler` stays true. The pulled reset (`reset_reader`, `:270-278`, from `reader` and the 1 s `on_reader_tick`,
`:284-296`) resets the reader's statements, not its transaction.

**Scenario.** A view traps after its handler's first read (any pure crash in the skeleton): the loop's reader keeps
that snapshot until the loop runs its next handler. Until then every read on the loop outside a handler (a write's
continuation, a pool's result) runs inside the stale transaction, since `tl_in_handler` is still true and `tl_txn`
set, and the WAL can't be checkpointed past it. On a quiet loop under writes that is the growth S0.6 measured
(+165 MB in 5 s) which D15 rule 3's timer exists to end; M2's per-handler transaction reopens it.

**Fix.** In `reset_reader` (both callers), also `end_txn(false)` when `tl_txn == r`, and clear `tl_in_handler`. Extend
`handler_transactions` in `sqlite_test.odin` with the timer's path.

### M2-11 · MEDIUM · past 4,096 clients, stream admission walks its whole client map on every admission

**Where.** `platform/stream/limits.odin:127`, `:166-171`: once `adm.clients` holds more than 4,096 entries, every
admission calls `sweep_clients` under `adm.mu`, which deletes only entries with no stream open and from an earlier
minute. Entries from the current minute stay, so in a busy minute each admission walks the whole map, frees nothing,
and the map grows until the minute turns. Keys are whole addresses (`web.client_key`,
`platform/web/routes.odin:74-84`): one IPv6 /64 is 2^64 of them.

**Scenario.** Connects to `/events?t=bot.health` (a guest may) from 20,000 addresses in one minute: about 2×10^8 map
steps under one lock, which every stream's open and close (`release`) and ops' job (`queued_total`) take. Loops stall
on it; past 10 s the watchdog exits 70.

**Fix.** Sweep at most once a minute, key an IPv6 client by its /64, and bound the map (503 past a cap on tracked
clients).

### M2-12 · LOW · M1-04's gaps: a continuation crashed twice, and one that crashes before `resume`

**Where.** In the memory family a store op's continuation runs inside its handler (`mem_store.finish`,
`platform/store/memory/memory.odin:32-34`), so `web.resume` sets the unwind (`platform/web/front.odin:345-358`) on the
handler's own invoke. A trap after `resume` runs the unwind, `http.response_crashed` → `connection_crashed` (a 500
queued, `Will_Close`; `vendor/odin-http/deferred.odin:68-73`, `server.odin:739-761`), and then the fork's crash path
calls `connection_crashed` again (`scanner.odin:296-297`), which now closes the socket with `shutdown(SEND)` while the
500 is still queued. Separately, chat's `posted` and `changed` publish before they resume
(`features/chat/web/web.odin:262`, `:370-373`): with a store whose continuations run later (a SQLite chat store at
M3), a crash there finds no unwind and leaves the connection deferred and unwatched, M1-04's original symptom.

**Scenario.** A bug in `chat_views.one` after resume, on `POST /chat/r/lobby`: the client gets a closed connection
instead of the 500 (suspected on io_uring, where the queued send is submitted on the next tick; confirm with the
`continuation` drill moved into a memory-store handler).

**Fix.** Make `connection_crashed` a no-op on a connection a crash already answered (or have `response_crashed` mark
it), and resume before any other work in a continuation.

### M2-13 · LOW · a crash while the bot finishes an answer locks the member out

**Where.** `features/bot/web/web.odin:307-322` handles `Bot_Done` inside the mock's tick
(`backend_mock/mock.odin:146-166`), whose `finish` (`:179-190`) has already removed the generation from its map. A
pure crash before `done(a)` (rendering the answer through markdown, say) skips `leave` (`web.odin:392-398`), so
`gens.active[member]` stays 1, and a Stop or the stream's close calls `cancel`, which no longer finds the generation.

**Scenario.** Every later ask by that member answers 429 "One answer at a time" until a restart or a new nickname;
the `Asking`, its stream and its `gens.owner` row leak.

**Fix.** Release the member's slot and the owner row first in the Done arm, then render and send.

### M2-14 · LOW · a HEAD to a stream route streams a body

**Where.** `vendor/odin-http/server.odin:924-930` hands a HEAD to the handler as a GET; `stream_begin`
(`stream.odin:93-164`) never looks at `req.is_head`, so the stream writes its body.

**Scenario.** `HEAD /events?t=bot.health` gets the heading, then `: open` and a heartbeat every 20 s, chunked, on a
connection that stays open; a client or proxy that trusts HEAD to carry no body reads them as the next response.
Admission counts it as a stream.

**Fix.** Refuse HEAD on `.Stream` rows in front (405, `Allow: GET`), or answer the heading alone.

### M2-15 · LOW · a refused WebSocket upgrade carries the 101's headers

`platform/stream/ws.odin:100-104` sets `upgrade`, `connection: Upgrade` and `sec-websocket-accept` before `open`
runs admission (`platform/stream/stream.odin:109-112`), which answers 503 or 429 on the same response
(`limits.odin:146-151`): a 429 that says `Connection: Upgrade`, with an accept key. Wrong framing (§19.2.3 LOW).
**Fix:** admit before setting the upgrade's headers.

### M2-16 · LOW · the lab writes a request's `after` into a URL with `esc`

`features/lab/web/web.odin:489-492` returns `?after=` as given, and `lab_views.live` writes it into
`hx-sse:connect="/events?…&amp;after=…"` with `esc` (`features/lab/views/views.odin:16-21`), where CLAUDE.md's
boundary asks for `url_encode`. `/lab/streams/live?after=1-1%26t%3Dlab.room%3Ax` renders a stream URL with a second
`t`. No exposure (every lab topic is public; `esc` keeps the attribute closed), but the page's stream URL is the
requester's to shape. **Fix:** accept only a cursor's shape (`parse_cursor`), or `url_encode` it.

### M2-17 · NIT · notify's "a path on this site" admits another origin

`features/notify/notify.odin:42` accepts any `ref` that starts with `/`, so `//host/…` and `/\host` pass, and the
Inbox writes the ref as a link (`notify/views/views.odin:51-55`). No producer passes user text today (chat builds the
ref from the slug and the id). Use `safe_next`'s rule (`accounts/identity_nick/routes.odin:98-104`): one definition.

### M2-18 · NIT · a topic has no `.Lan_Only`

`/admin/ops` is `.Lan_Only` (`features/ops/web/web.odin:155-157`); its topic `ops.panel` checks `.Admin_Ops` alone
(`:162-164`). An Admin by `ACCOUNTS_NICK_ADMIN_CIDRS` outside `LAN_CIDRS` gets 404 on the page and the 1 Hz panel on
`/events?t=ops.panel`. Give `hub.Topic` the flag, or have boot refuse admin CIDRs outside the LAN's.

### M2-19 · NIT · two numbers from a request parsed outside `parse_digits`' bounds

`features/bot/web/web.odin:366` parses the generation id with `strconv.parse_u64_of_base` (it wraps past 64 bits;
harmless, the owner check holds). `features/lab/web/web.odin:329-330` adds a header's number, up to `max(int)`, to a

### M2-20 · NIT · init's scratch build skips two of check's gates

`tools/init/verify.odin:58` holds the scratch copy to `tools/check profile routes topics exts`; CI runs `all`, which
adds `imports` and `contracts`. A plan that breaks the layering passes verify and fails the new project's first CI

### M2-21 · NIT · F-17's arena return misses a POST stream

`vendor/odin-http/server.odin:930-935` gives the request arena back only when the stream began in a handler called

#### M2-22 · HIGH · JSON5 syntax walks past `ws_json`'s depth scan

**Where.** `platform/stream/ws.odin:36-58`. `ws_json` calls `json.unmarshal(data, out, allocator = …)` with the default
specification, which is `.JSON5` (core:encoding/json `types.odin:49`). Under JSON5 the tokenizer reads `'…'` as a
string (`tokenizer.odin:296-302`) and skips `//` and `/* */` comments (`:342-361`); the scan knows only `"…"` strings.
A `"` inside a single-quoted string or a comment starts a string for the scan that the parser never sees, and the scan
counts every bracket after it as string content. `unmarshal_any` then runs `is_valid` (`unmarshal.odin:125`), whose
`validate_value` → `validate_array` recursion (`validator.odin:68-130`) is the one M2-01 describes.

**Scenario.** One text frame to `/lab/ws/chat`: `{"message":"x","headers":/*"*/` followed by 65,000 `[`, 65,031 bytes
in all. The scan sees depth 1 and passes it. The validator recurses 65,000 levels, the loop's stack overflows as M2-01
describes, and three addresses reach GUARD_BURST and exit 70, with no identity needed. `'"'` in place of the comment
works the same way, and chat's socket takes the same frame. A second vector needs no bracket at all: JSON5 skips a
comment with `return get_token(t)` (`tokenizer.odin:349`, `:356`), a frame per comment, so 21,845 × `//\n` recurse as
deep. That is certain on a build at the compiler's default optimisation (`build.sh` without `-o`, the suites' builds).
At `-o:speed` it is suspected, because it depends on LLVM turning that self tail call into a loop.

**Fix.** Call `json.unmarshal(data, out, spec = .JSON, allocator = context.temp_allocator)`. hx-ws sends RFC 8259 JSON,
and under `.JSON` a `'` or a `/` is an illegal token that fails validation at once. The scan and the tokenizer then
agree on strings: both end one at an unescaped `"`, and a raw newline ends the tokenizer's as invalid. Add both payloads
to `ws_json_refuses_deep_nesting_before_it_parses` and to the drills' `wsdata` phase.

#### M2-23 · MEDIUM · the SSE backlog budget counts HTML, not what the stream queues

**Where.** `platform/hub/events.odin:118-128` and `:157-160` sum `len(html)` against `stream.backlog_budget()` (half of
`STREAM_MAX_QUEUED`). They then write each item through `sse_event`, which puts `data: ` and a newline around every line
(`platform/stream/sse.odin:48-56`), so a one-byte line break costs seven. Live delivery has the same gap. `publish`
bounds a message's HTML by `MAX_MESSAGE` (64 KiB, `hub.odin:211`), and `deliver` writes its SSE encoding in one write
(`:383-384`). The fork refuses that write past the queue cap and ends the stream Too_Slow
(`vendor/odin-http/stream.odin:171-174`).

**Scenario.** One unauthenticated `POST /lab/publish?t=lab.feed:live` with `id=a` and a `text` of 60,000 line feeds:
- Its HTML is about 60 KB, under `MAX_MESSAGE` and under the budget. Its SSE event is about 420 KB.
- Every SSE subscriber of `lab.feed:live` is closed Too_Slow when the message arrives. That includes the default
  `/lab/streams/live` page (`lab/web/web.odin:109`).
- Every reconnect carries an older `Last-Event-ID`, so the replay writes the message again and the stream is closed
  again, until 256 later messages or the ten-minute sweep take it out of the ring.

Chat has the same exposure, because a body is trimmed but keeps its inner line breaks (`chat.odin:168-177`). About
thirty messages of `a` and a line feed alternating, 2,000 runes each, can be posted in a minute. Each renders to about
2.7 KB of HTML and about 8.7 KB of SSE. A member on the SSE transport whose `#live` missed them gets a replay well
within the budget that queues past the cap. That is M2-03's loop, for every page that was away.

**Fix.** Measure what is written: encode the replay's events first and sum their lengths, or count `len(html)` plus
seven bytes per line plus the `id:` line. Have `publish` refuse a message whose SSE encoding would pass the budget, so a
single live message can't pass the cap either.

#### M2-24 · MEDIUM · the rings' budget counts only HTML, and each eviction walks every ring

**Where.** `platform/hub/hub.odin:268-278`; `ring.odin:66-74`. `rings_held` adds `len(m.html)` only. A message also
holds its `Msg`, its topic copy and a ring slot, and a ring holds its struct, its topic copy, its `msgs` array and a map
slot. A one-message ring from the smallest lab publish counts 52 bytes and holds roughly ten times that. Past
`HUB_RINGS_BYTES`, every publish evicts through `ring_evict_oldest`, which walks the whole rings map under `h.mu` to find
the oldest `last_ns`, once for each ring it evicts.

**Scenario.** An attacker POSTs to `/lab/publish?t=lab.room:<k>` with an empty `text` and a new key each time:
- Each ring counts 52 bytes, so the 64 MiB budget admits about 1.3 million rings, roughly 0.7 GB in fact.
- About 110 client keys reach that within the ten-minute idle window at the lab's 1,200 a minute. One IPv6 /57 has 128.
- From then on every publish dereferences about 1.3 million scattered rings under `h.mu` before it lets go: the
  attacker's, and also chat posts, presence, the ops job and `lab.bus`. That is tens of milliseconds a publish.
- Every `/events` connect waits on the same mutex. Loops spend their time waiting on it, so every route they serve
  crawls until the sweep takes the idle rings, ten minutes after the attack stops.

An exit 70 needs one loop to wait past STALL (10 s), which is suspected only: the mutex is not fair, but four
contenders rarely starve one that long.

**Fix.** Keep the rings on a list in publish order: a ring moves to the back when it is published to, and eviction takes
the front, in O(1). Count each message's and each ring's fixed cost in `rings_held`, or cap the number of rings.

#### M2-25 · LOW · an IPv4-mapped address keys to one /64, shared by every IPv4 client

**Where.** `platform/web/routes.odin:76-87` keys an `IP6_Address` by its first eight bytes. `client_of` reads a trusted
proxy's `X-Real-IP` through `net.parse_address` (`web/front.odin:229-231`). That tries IPv6 first and returns
`::ffff:a.b.c.d` as an IPv6 address (core:net `addr.odin:380-388`).

**Scenario.** A trusted proxy reports IPv4 peers in mapped form (HAProxy bound `v4v6`, or nginx with `ipv6only=off`).
Every IPv4 client then has one key, the hash of eight zero bytes, for the whole site, so they share:
- one admission count: the 21st stream opened anywhere in a minute gets 429;
- one guest bot limit;
- one lab publish limit;
- one CSP-report limit.

Before `e514039` the full 16 bytes kept them apart. The proxies CI exercises report plain IPv4.

**Fix.** Unmap `::ffff:0:0/96` to an `IP4_Address` in `client_of`, or in `client_key` before it takes the /64.

#### M2-26 · LOW · a resumed multipart feed past the budget drops messages silently

**Where.** `features/chat/transport_multipart/multipart.odin:45-49`; `chat/views/views.odin:184-193`. A reconnect with
`HX-Last-Part-ID` gets the newest messages that fit `backlog_budget()`, under the newest message's id. The older ones it
missed are dropped. The multipart transport has no resync, while the SSE transport's log refetches on `resync`
(`transport_sse/sse.odin:26`).

**Scenario.** A member on multipart drops off while 128 KiB of messages arrive: about twelve 2,000-rune messages of
`&`, or a few hundred short ones. On reconnect the oldest missed messages never appear, and the feed's id is already past
them, so only a reload shows them.

**Fix.** Past the budget, send a part that makes the log refetch (`HX-Trigger`, as a kick's part does), or send the rest
as further parts once the first is out.

#### M2-27 · LOW · a crash before a loop opens its reader escapes M2-10's reset

**Where.** `platform/store/sqlite/sqlite.odin:196-200`, `:247-268`. `handler_began` marks the handler in, and a crash
skips `handler_ended`. Suppose the loop had no reader yet, or the store's generation changed. The next read then opens a
reader with `seen` at the current recovery count (`:257`), `pull_reset` finds nothing to do, and `tl_in_handler` stays
true.

**Scenario.** On the skeleton, a loop's first handlers queue writes without reading, and one of them traps. Then a
write's continuation on that loop reads: `updated` → `answer_updated` → `contacts.detail`
(`contacts/web/web.odin:266`). `read` begins a transaction for it (`sqlite.odin:187`) that nothing commits, and the
reader's timer doesn't end it either. It lasts until that loop runs another handler. On a quiet loop this is M2-10's
pinned WAL.

**Fix.** Treat the flag as stale once the thread has recovered since the handler began. Record `guard.recoveries()` in
`handler_began`, and have `read` begin a handler transaction only while that count is unchanged.

#### M2-28 · NIT · a crashed connection's 500 has no send deadline

`vendor/odin-http/server.odin:761`. With M2-12's flag, the completion of this send is the only thing that closes a
crashed connection while the server is serving. The send sets no `send_deadline`. A peer that has stopped reading with a
full window keeps the connection, and its slot under the connection cap, until it reads or the drain deadline arrives.
**Fix:** `c.send_deadline = _send_deadline(c)` before the send, as every other send has (M1-02).

#### M2-29 · NIT · six "Held by" entries name tests that never reach the fix

M2-05 names the existing presence and typing specs. M2-06 names the stores' tests, but nothing pins `MAX_OWNERS` or
`MAX_USERS`. M2-08 names the chat domain's tests, which are unchanged. M2-09 names the bot specs, which are unchanged

clients nor a /64. M2-20 names `odin test tools/init`, which never runs `verify_profile`. **Fix:** a unit test per bound

addresses in one /64 and for a mapped one), and a Held-by column that says "read" where no test reaches the fix.

### The fixes

- **M2-22 · unsound (M2-30).** `spec = .JSON` (`platform/stream/ws.odin:60`) closes both vectors the re-read found. A
  `'` or a `/` is now a one-rune illegal token (`tokenizer.odin:296-300`, `:342-344`). `get_token`'s only calls to

  Strings mostly agree as well:
  - after a `\` the tokenizer consumes the next rune whatever it is (`scan_escape`, `:107-129`), as the scan skips the

  the old default, and the third would parse. None has a raw line feed inside a string, and neither has the drills'
  three payloads.

#### M2-30 · HIGH · a raw line feed in a key walks past `ws_json`'s depth scan

**Where.** `platform/stream/ws.odin:41-59`. Inside a string the scan stops only at an unescaped `"`. The strict
tokenizer also stops at a raw line feed, with three effects:
- it reports `String_Not_Terminated`;
- it keeps the token's kind `.String`;
- it leaves the line feed to be skipped as whitespace (core:encoding/json `tokenizer.odin:302-323`, `:136-143`).

The validator checks a string only where it is a value (`validator.odin:102-104`). Where it is an object key,
`validate_object_key` accepts any `.String` token (`:26-34`) through `expect_token`, which compares kinds only
(`parser.odin:92-100`). The parse therefore continues after the cut key. The scan is still inside the string and
counts nothing after it. `unmarshal_any` runs `is_valid` first (`unmarshal.odin:125`), and that recursion is the one
M2-01 describes.

**Scenario.** One text frame to `/lab/ws/chat`: `{"a`, a line feed, `:`, then 65,000 `[`. That is 65,005 bytes of valid
UTF-8 with no further `"`. The scan sees depth 1 and lets it through. The validator reads the key `"a` and the colon,
then recurses 65,000 levels through `validate_value` and `validate_array`. The loop's stack overflows on Windows for
certain. On Linux the reasoning is M2-01's, so it is suspected at `-o:speed`. Each socket dies on its first such frame
(1011), so one client key costs 20 recoveries a calendar minute. Three IPv4 addresses, or three /64s, pass GUARD_BURST
and the process exits 70, with no identity needed. Chat's socket accepts the same frame. Neither
`ws_json_refuses_deep_nesting_before_it_parses` nor the drills' `wsdata` phase sends a raw line feed inside a string.

**Fix.** In the scan, refuse any byte below 0x20 inside a string, checked before the escape test. RFC 8259 allows none
of them unescaped. With none possible, the scan's strings end exactly where the tokenizer's do. Add this frame to the
unit test and to `wsdata`.

- **M2-30 · sound.** Both halves hold, and either one alone stops M2-30's frame.
  - *The scan.* `ws_json` (`platform/stream/ws.odin:44-76`) now refuses a byte below 0x20 inside a string, before the

#### M2-33 · LOW · `json.unmarshal` takes stack for every key, and neither bound counts keys

**Where.** core:encoding/json `unmarshal.odin:548-550`, inside `unmarshal_object`'s `struct_loop` (`:542`):
`field_used := intrinsics.alloca(field_used_bytes + 1, 1)`, where `field_used_bytes` is `(size_of(T) + 7) / 8`.
- The compiler lowers the intrinsic to an LLVM array alloca at the point of the call. Its backend never saves or
  restores the stack pointer (dev-2026-06's `src/llvm_backend_proc.cpp:3351-3360`; the word appears nowhere else in its
  source).
- An alloca in a loop body therefore keeps every iteration's block until the procedure returns: at least 16 bytes a
  key on x86-64.
- Each key also gets a fresh, zeroed block, so the code's own `Multiple_Use_Field` check can never fire.

`platform/stream/ws.odin:44-75` bounds brackets and depth, not keys.

**Scenario.** Both shipped handlers fill a 16-byte struct (`chat/transport_ws/ws.odin:78-80`,
`lab/web/web.odin:254`). That is 3 bytes a key, rounded to 16. A 64 KiB frame of `{"":0,"":0,…}` holds about 13,100
keys, so about 205 KiB of one call's stack. The struct has no such field, but the alloca comes before the lookup.
- *Today.* With the depth scan's 17 levels this fits a 1 MiB Windows loop easily, so nothing crashes. It still takes a
  fifth of the stack that WS_JSON_OPENS' margin assumed was free.
- *A fork.* `ws_json` is generic and is documented as the way every handler reads a client's JSON. A `T` of about 505
  bytes or more (32 strings) pays 80 bytes a key. One flat frame then passes both bounds and overflows a Windows loop's
  1 MiB. On Linux, a loop's 8 MiB would take a `T` near 5 KB.

**Fix.** Bound the keys in the scan. Its strings now agree with the tokenizer's, so it can count `:` outside strings
and refuse past, say, 64; hx-ws's envelope has a handful. Beside it, `#assert(size_of(T) <= 64)`. The alternative is to

#### M2-35 · LOW · SSE's resync and the poll transport also upsert across a gap

**Where.** `features/chat/transport_sse/sse.odin:26`; `transport_poll/poll.odin:35-63`; `chat/views/views.odin:174-179`;
`stores/memory/chat/store.odin:125-135`. M2-31's fix reaches multipart only:
- SSE's `resync` refetches `/since` with no tag, which answers the room's last SNAPSHOT (50), upserted: `partial`'s

  let go, and the answer upserts too.

**Scenario.**
- *SSE.* Bob has a busy room open and his laptop sleeps while 300 short messages are posted. On waking, `/events`

D37's restart still holds: a new process's versions start above every old tag, and its rooms have let nothing go.
