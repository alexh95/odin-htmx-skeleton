# M4 audit: accounts, sessions and the second factor, authz, audit, modules, and Houston's two hosts

An independent audit of milestone M4 (PLAN §19.2), by an agent that did not write the code. It applies the review
rubric (§19.2.2), the severity scale (§19.2.3) and the crash-zone rules of D15 to everything M4 adds: accounts with
passwords and server-side sessions (`features/accounts/**`, `stores/sqlite/accounts`), argon2id on its pool
(`platform/password`), TOTP and recovery codes (`platform/totp`, `identity_accounts/second.odin`), invites, resets and
`/admin/accounts`, `envadmin`, authz's step-up and front's route rules, the audit log (`features/audit`, both
`store:audit` members), `/admin/modules`, the hub's member topics and `hub.revoke`, `cmd/full` with its two hosts,
the contacts demo's cap and nightly reset, `starter-full` in `deploy/`, `full-vanilla`, and `tools/init`'s
`--pairwise`/`--random` and its gated-feature refusal. The brief asked for most attention on session handling,
timing oracles, CSRF and WebSocket origins, the session-free lab host, step-up, rate limits, privilege escalation,
audit integrity, escaping, allocators, crash zones and secrets; the last section answers each.

**Method.** Read-only. Another session's performance run may share the machine, so nothing was built, checked,
tested or run: no `odin build/check/test`, no `build.sh`, no server, no node or Playwright, no k6, no Docker. Every
finding comes from reading the source at `d136601` (`d13660121aaa4ab1544be30fe0d8a9b2ed8957a6`, HEAD when the read
began and when it ended); line numbers are at that commit. The one untracked file in the tree, a perf CSV, was not
read. Where a finding rests on the toolchain's own code (core:encoding/base64, core:encoding/base32, the runtime's
`make` checks), that code was read at the installed Odin (dev-2026-10, the pinned `84bc3fc`). Where reading could not
settle a point the finding says "suspected" and names what would confirm it. `docs/private/` and
`deploy/promote.local.psd1` were not opened; host names stand as placeholders (`<houston host>`, `<lab host>`,
`<site domain>`).

**Result.** 0 CRITICAL, 1 HIGH, 3 MEDIUM, 9 LOW, 3 NIT. M4 cannot exit until M4-01 is fixed (§19.2.1: exit needs 0
open CRITICAL or HIGH). M4-01 is not a crash: it is rated HIGH because it defeats the step-up gate every admin write
stands behind, and because the takeover it allows has no way back in the product (M4-10). M4 closes none of the earlier
findings in code; the one its commits name, M3-03, was deferred to M12 by Alex, and M4 raises its stakes (see "Earlier
findings").

### M4-01 · HIGH · re-enrolling TOTP needs no step-up, so a session buys step-up and the account

**Where.** `identity_accounts/routes.odin:44` mounts `{.Post, "/accounts/totp", totp_on, .Account_Self, {.Fragment},
512}`: no `.Step_Up`, while its siblings `/accounts/totp/codes` and `/accounts/totp/off` (`:45-46`) have it. `totp_on`
(`second.odin:232-242`) decodes the `secret` the form posts back, checks the code against it, and calls `set_totp`
(`:272-312`) with it. Nothing checks that two-step sign-in is off: the page only stops *showing* the setup form when it
is on (`:217-225`). The store's `set_totp` (`stores/sqlite/accounts/store.odin:325-349`) overwrites `totp_secret`
unconditionally, deletes every recovery code (`SQL_DROP_CODES`) and stores ten new ones. The secret is also the
client's choice: the server never remembers which one it offered.

**Scenario.** Someone holds a member's session for a while: a laptop left signed in, a borrowed browser, a cookie
copied off a shared machine. They have no password and no authenticator. With curl and the cookie (no `Origin`, no
`Sec-Fetch-Site`, so `same_origin` passes) they `POST /accounts/totp` with a secret of their own and its current code.
The answer is ten fresh recovery codes; the owner's app and the owner's recovery codes are now worthless. Then
`POST /step-up` with a six-digit code from their own app (`second.odin:151-159`): `step_up_at` is now, so every
`.Step_Up` row opens: `/accounts/totp/off`, `/accounts/totp/codes` and, if the session is an Admin's and the request
comes from the LAN, every write on `/admin/accounts` (roles, disable, invites, reset codes). When the session ends,
the owner can't sign in again: the password is right, the code step (`second.odin:75-101`) wants a code from a secret
only the intruder has. An admin's `/reset` code doesn't help (M4-10): it sets the password and leaves TOTP on. If the
account was the only enabled Admin, Houston has no admin left who can act, and `bootstrap` doesn't step in, because
the account is still an enabled admin (`store.odin:217-224`). The only way back is an edit of the database file.

This is the step-up gate's whole purpose (§17.1: a recent password or code before a sensitive write) undone by one
write it doesn't cover, and it turns a temporary session into a permanent account. Reading settles it; an e2e case
confirms it in a minute: enrol, then post a second secret and code to `/accounts/totp` on the same session.

**Fix.** Refuse `totp_on` when `u.totp_secret != ""` (422: "two-step sign-in is on: turn it off first"), and make the
store's enrolment conditional (`UPDATE users SET totp_secret = ?, totp_last_step = ? WHERE id = ? AND totp_secret =
''`, `.Constraint` on no change) so two racing enrolments can't replace each other. Mark `/accounts/totp` `.Step_Up`
as well: turning a factor on is as sensitive as turning it off, and an Admin's role hangs on it. Optionally sign the
offered secret (as the pending token is signed) so the client can't choose it. A `totp.spec` case: a second
enrolment on an account with TOTP on is refused and the first app's codes still sign in.

### M4-02 · MEDIUM · a MAC of `=` traps `base64.decode`, unauthenticated

**Where.** `read_pending` (`identity_accounts/second.odin:47-61`) and envadmin's `read` (`envadmin.odin:122-135`)
split the token at its last `.` and pass the rest, as sent, to `base64.decode(…, DEC_URL_TABLE, nil,
context.temp_allocator)` with no options (`second.odin:54`, `envadmin.odin:128`). With no options core's
`validate_strict_decode` checks nothing (`base64.odin:288-291`), and `decode` (`:373-390`) takes `out_length :=
decoded_len(data)`, which is `((len * 6) >> 3) - padding` (`:521-537`). For `"="` that is `0 - 1 = -1`, for `"=="`
`1 - 2 = -1`; `out_length == 0` is the only early return, so `make([]byte, -1, allocator)` runs, and the runtime's
`make_slice_error_loc` (`base/runtime/error_checks.odin:342-354`) calls `bounds_trap()`.

**Scenario.** `POST /login/code` with `pending=1.%3D` (any `<digits>.=`), from anyone: `second_factor` spends one of the
client's sign-in attempts (`:77`), then `read_pending` traps before the MAC is compared. On an envadmin build it is
cheaper: a `Cookie: admin=1.=` on any routed request reaches `load_viewer` (`envadmin.odin:99-105`) from `front`'s
`admit`, before any rule or limit, so every request so marked traps. Both traps are pure by D15's counters (no lock
held, no op posted, outside SQLite; on `/login/code` a viewer's reader transaction may be open, which M2-10's fix
resets), so the guard answers 500 and serving goes on. The cost is a crash line at `Error` and the crash counters per
request, at the rate the sender likes on envadmin, and a rubric item 2 breach ("no panics on external input"). It is
not rated higher because the guard holds; were the trap ever moved inside a lock or a store read, it would be an exit
70 per request. Certain from reading; a unit case `read_pending("1.=")` (and `read("1.=", key, now)`) traps today.

**Fix.** Never decode the attacker's MAC: encode ours (`base64.encode(mac[:], ENC_URL_TABLE, …, {.No_Padding})`) and
compare the two strings with `crypto.compare_constant_time` after a length check (43 characters). Or check `len ==
43` before decoding and pass `{.No_Padding}`, which makes `validate_strict_decode` refuse any `=`. Add `"="`, `"=="`,
`"1.="`, `"1.=="` and a 44-character MAC to both unit tests, and see M4-13.

### M4-03 · MEDIUM · one sign-in budget anyone can spend, and a backoff anyone can hold shut

**Where.** `logins_all` (`routes.odin:69`) is one `web.Limit` of 40 per 15 minutes keyed by `0`: one bucket for the
whole process. `sign_in` (`:147-154`) and `admit_attempt` (`second.odin:105-115`), which `/login/code` (`:77`) and
`/step-up` (`:136`) call, count every attempt against it after the per-client limit (5 per 15 minutes) passes,
before the form is even parsed. Separately, a wrong password or code for a known account sets `backoff_until` (`backoff_ms`,
`accounts.odin:81-84`: free for three, then 1 s doubling to 5 minutes) and, while it holds, every sign-in, code and
step-up for that account answers 429 (`routes.odin:167-171`, `second.odin:87-90`, `:142-145`); the counter resets only
on a successful sign-in (`SQL_CLEAR` in `open_session`). `/reset` (`members.odin:226-248`) is limited only per
client (10 an hour): a known name and any well-formed code reach the argon pool, which hashes before the write finds
the code wrong. `limit_hit` forgets every key once 4,096 are tracked (`platform/web/limit.odin:34`).

**Scenario.** (a) Eight client keys, a /64 each over IPv6 or eight IPv4 addresses, send 5 junk `POST /login` each at
the start of every 15-minute window: the 40 are spent, and for the rest of the window every sign-in, every code step
and every step-up on Houston answers 429. Step-up is what every write on `/admin/accounts` asks for once ten minutes
have passed since sign-in, so the admins can't act either. 40 requests per 15 minutes, indefinitely. (b) The default
admin name is `admin` (`ACCOUNTS_ADMIN_NAME`), and members' names show on pages. A client sends a wrong password for
`admin` whenever its backoff ends: twelve requests over about a quarter of an hour reach the 5-minute ceiling (three
client keys cover that ramp within the per-client limit), then one every five minutes keeps it there, which one
client's allowance of 5 per 15 minutes covers. The real admin's sign-in and step-up answer
429 for as long as it goes on; the module comment's "never a lockout" holds for a guesser, not for someone who wants
the door shut. (c) Clients with many keys post `/reset` with the admin's name: each costs a 19 MiB, 20-30 ms argon
hash on a pool of one or two threads with a queue of 32, and past it every sign-in answers "Busy" (503). Once 4,096
keys have been seen, every client's per-client count starts over.

**Fix.** For (a): keep a global ceiling for the argon pool's sake, but don't let a refusal there apply to everyone
alike: count only attempts that reach the pool (after the backoff check), exempt a step-up (it already needs a live
session, and the per-account backoff guards it), and prefer per-account plus per-/24 or per-/48 buckets over one
global bucket. For (b): let a correct password through the backoff when it comes from a client that has never failed
for that account (a per-client-and-account backoff, OWASP's "device cookie" idea), or cap the backoff's reach to the
clients that earned it. For (c): `/reset` should find the live code for the account before hashing (a read,
`SQL_SPEND_RESET`'s condition as a `SELECT`), and the pool's queue refusal should not be reachable without a valid
code. Note the trade-off with M4-05 (the backoff's 429 is also an oracle).

### M4-04 · MEDIUM · audit entries are written after the fact, and only for a client that waited

**Where.** Every M4 audit entry is appended in the op's continuation, after `web.resume` returned a response:
`acted` (`admin.odin:105-126`: `if res == nil { return }` at `:107-108`, the append at `:112`), `opened`
(`routes.odin:231-257`), `closed` (`:350-374`), the step-up's continuation (`second.odin:179-199`), `set_totp`'s
(`:284-303`), `registered` (`members.odin:188-212`) and `reset_done` (`:251-271`). The change itself has already
committed on the writer. `audit_store.append` queues a separate op and returns false when the writer's queue is full
(`audit/models/models.odin:48-50`: "the entry is lost"); every caller ignores the result.

**Scenario.** An admin, or whoever holds an admin's session and step-up (M4-01), sends `POST
/admin/accounts/7/role` with `role=Admin` and an `HX-Prompt`, and closes the connection as soon as the request is
written (curl with a short `--max-time`, or a raw socket that sends and resets). The writer commits the role change a
few milliseconds later; the fork's deferred response has seen the close (`response_defer` watches the connection), so
`resume` returns nil, the continuation frees the op, and `audit_log` never hears of it. The same goes for a disable, a
reset code, an invite, TOTP off and new recovery codes. Under write load the queue can also refuse the append after
the change went in, with nothing logged at all. The triggers make the table append-only, but what never reaches it
isn't protected. Whether the close beats the commit is a race (suspected: likely on most tries, since the writer's
commit includes a WAL write); a drill confirms it: queue a role change, reset the socket at once, read `audit_log`.

**Fix.** Write the entry in the same transaction as the change: give each accounts op its `m.Entry` and let its `run`
insert into `audit_log` (a small `audit_sql.append_in(entry)` helper the writer-side code can call, or the audit row
as one more statement of the op), so an entry exists exactly when the change does. At the least, move each append
above the `if res == nil { return }` and log at `Error` when `append` returns false.

### M4-05 · LOW · which usernames exist shows through the backoff and through `/reset`'s timing

**Where.** `sign_in` answers 429 "Too many wrong passwords" only for a known account in backoff (`routes.odin:167-171`);
an unknown name never backs off. `/reset` refuses an unknown name at once (`members.odin:235-241`) and hashes for a
known one before the write refuses a wrong code.

**Scenario.** Four wrong passwords in a row for a name: the fourth answers 429 within a second if the name exists,
422 if not. On `/reset`, a known name answers 20-30 ms later than an unknown one. Both fit within the per-client limits.
The sign-in path itself is careful (the dummy verify, `password.odin:68-87`), so these are the two leaks left.

**Fix.** Back off by name, not only by account: keep the backoff for unknown names too (an in-memory map keyed by the
lowercased name, bounded like `web.Limit`), or answer a backed-off account with the same 422 after the same dummy
verify. On `/reset`, verify the code before hashing (M4-03's fix (c)) and answer an unknown name after the same read.

### M4-06 · LOW · an op's statements aren't one unit

**Where.** The writer runs a batch of ops in one transaction; "a write that fails alone … fails alone, because SQLite
rolls back only the failing statement" (`writer.odin:9-11`). M4's ops are several statements each, and the earlier
ones stay when a later one fails: `register` (`store.odin:366-407`) spends the invite (`SQL_SPEND_INVITE`) and then
inserts the user; `set_totp` (`:325-349`) sets the secret, drops the codes, adds ten; `redeem_reset` (`:515-534`)
spends the code, sets the password, ends the sessions. The model says otherwise ("in one write", `models.odin:40-42`):
the statements do commit in one transaction, but they don't fail as one.

**Scenario.** Two people register the same name from one invite link a moment apart (or one name differing only in
case: `username` is `COLLATE NOCASE`, `migrations/0001_accounts.sql:6`). Both pass `user_by_name`, both reach the writer;
the second's `INSERT` fails `.Constraint` after its `UPDATE … uses = uses + 1` stood: a single-use invite is used up
and nobody joined with it, and the answer says "That username is taken". For `set_totp`, a failure among the ten
inserts (a duplicate code: improbable at 40 bits) would leave TOTP on with fewer codes than shown.

**Fix.** Run each op's `run` inside `SAVEPOINT op; … RELEASE op`, and `ROLLBACK TO op` when it sets `o.err` (the
writer can do it around `op.run(op)` once for every feature), or order `register` so the insert comes first.

### M4-07 · LOW · the audit's client id is the address, lightly disguised

**Where.** `client_id` (`identity_accounts/routes.odin:378-382`) writes `web.client_key(c.client)` as hex into every
entry's `client_id`, "the hashed address, never the address". `client_key` (`platform/web/routes.odin:76-90`) is
`hash.fnv64a` of the four IPv4 bytes (or the /64 prefix), with no key; `web.client_id`, which the access log uses, is
keyed (`sec.cid_key`). `audit_log` keeps a row 400 days and refuses its deletion (`0001_audit.sql`'s triggers), and
`/admin/audit/export` hands the column out as CSV.

**Scenario.** Anyone holding an export, a database backup (M4-12) or the volume hashes the 2^32 IPv4 addresses with
FNV-64a, which takes seconds, and reads every failed and successful sign-in's address back, for 400 days, with no
way to erase a row. That contradicts the stated privacy rule (§17.7, and "never the address") and would matter for a
data-protection request.

**Fix.** Store `web.client_id`'s keyed hash (or an HMAC with a key from the environment that survives restarts, so a
client's entries still group), and say in the README how long it identifies anyone.

### M4-08 · LOW · `sid`, not `__Host-sid`: a sibling origin can plant one

**Where.** The cookie is `sid=…; Path=/; HttpOnly; SameSite=Lax` (`identity_accounts/accounts.odin:28`, `:178-187`),
host-only. `authz.cookie` (`platform/authz/authz.odin:131-138`) returns the first `sid` in the header.

**Scenario.** The lab host exists so that an eval-capable page never shares an *origin* with a session, and that
holds; but it shares a *site*. `<lab host>` and `<houston host>` are siblings under `<site domain>`, as are the other
witnesses and games. Script running on any of them (an XSS there, or the scripting lab's own code if it ever takes
input) can set `document.cookie = "sid=<a session of the attacker's>; Domain=<site domain>; Path=/accounts"`. The
browser sends that cookie to Houston too, and the more specific path sorts first, so on `/accounts/*` the victim is
the attacker's member: their two-step setup, profile and theme writes land in the attacker's account (login CSRF).
`same_origin` stops the sibling from *posting*, not from *planting*.

**Fix.** Name the cookie `__Host-sid` when it is `Secure` (which `__Host-` requires; keep `sid` only for
`COOKIE_SECURE=0`), which the browser refuses to set with a `Domain` or a narrower `Path`. The same for envadmin's
`admin`.

### M4-09 · LOW · a sign-out, a revoke or a reset leaves that session's stream open

**Where.** `hub.revoke` (`platform/hub/hub.odin:245-253`) is called only by `acted` for a role change or a disable
(`admin.odin:114`). `closing`/`closed` (`routes.odin:330-374`, a sign-out or a member's revoke) and `reset_done`
(`members.odin:251-271`, which ends every session) end the rows only. `/events` checks the viewer once, at admission.

**Scenario.** A member sees an unknown device on `/accounts/sessions` and revokes it, or an admin's reset code is
redeemed because the account was taken over: the intruder's open page keeps its `#live` stream, with the member's
own topic (`accounts.user:<id>`, `member = true`) and whatever page topics it opened, until it drops on its own.
Today the member topic carries only kicks; at M5+ it carries the member's notices. Separately, a stream admitted by a
request whose viewer was loaded just before a role change committed subscribes after the kick and keeps the old
grant. TODO's slice 8 already says the first case for a member's revoke; a reset and a sign-out aren't mentioned.

**Fix.** Call `hub.revoke(user_id)` after a reset too (it ends every session); for a single session, give the hub
a per-session key (the session's hash prefix as a `member` key, or a `session:` topic) so a revoke and a sign-out can
end exactly that device's streams. For the race, re-check the session when `/events` subscribes, after `join_loop`.

### M4-10 · LOW · no way back from a lost authenticator

**Where.** A reset (`members.odin:226-248`, `store.odin:515-534`) sets the password and ends sessions, and keeps
`totp_secret`; `/admin/accounts` has role, disable, enable, reset code and invites (`admin.odin`), and nothing turns a
member's TOTP off. `/accounts/totp/off` needs the member signed in.

**Scenario.** A member loses their phone and their recovery codes (or M4-01 happens to them): no admin action lets
them in again. The admin can only disable the account. For the only Admin it means an edit of the database.

**Fix.** An admin action "turn two-step off" on `/admin/accounts` (LAN, step-up, reason, audited, and a revoke), or
a reset code that also clears TOTP when the admin ticks it. Either closes M4-01's dead end.

### M4-11 · LOW · `ACCOUNTS_ADMIN_NAME` is taken as it is

**Where.** `bootstrap` (`identity_accounts/accounts.odin:106-132`) inserts the first admin with
`ACCOUNTS_ADMIN_NAME` as both username and display (`store.odin:217-236`), never through `check_username` or
`clean_name`. When the insert fails, `bootstrap_admin` returns `.Failed` and `bootstrap` exits 70 (`:122-125`).

**Scenario.** A Houston started with `ACCOUNTS_REGISTRATION=open` and no hash yet: someone registers `admin`. When the
hash is set, every boot finds no enabled admin, the `INSERT` fails `UNIQUE`, and the process exits 70; compose
restarts it into the same exit. A name with spaces, `<` or a bidi override is also accepted as an admin's name, and a
long one lands in `ACT_BYTES`-sized op arenas (`admin.odin:101`) whose slack it can outgrow.

**Fix.** Check the name at boot with `check_username` (78 on a bad one, as a bad hash does), and when the name is
taken by a non-admin, say so and refuse to boot with a message rather than exit 70 in a loop.

### M4-12 · LOW · Houston's snapshot runs an unpinned image beside the accounts database

**Where.** M4 turns on promote's snapshot for `starter-full` (`promote.ps1:60`). Its pruning step (`:176`) runs `docker
run --rm --volumes-from <id> --entrypoint /bin/sh busybox …`: `busybox` by its mutable `latest` tag, as root, with
the `full-data` volume mounted, the one holding `data.db` and `backups/pre-*.db`. M3-08's re-read left the busybox pin
open for "M4's first snapshot" (TODO); it is still unpinned. The backups are whole copies of the database, which holds
`totp_secret` in the clear (`0001_accounts.sql`) and recovery codes as unsalted SHA-256 of 40-bit codes
(`accounts.odin:218-230`), so a copy yields the second factor outright. The `admin_hash` secret is a bind of
`./admin-hash` (`compose.yaml:159-162`), which the container's UID 10001 can read only if the host file is readable
by it: likely world-readable in practice (suspected; `stat` on the host confirms).

**Scenario.** A compromised or swapped `busybox:latest` pulled at the next promote runs with the accounts database
mounted read-write. Separately, a leaked backup gives an attacker TOTP secrets, so only argon2id stands between them
and the accounts.

**Fix.** Pin `busybox@sha256:…` (or prune with the app image's own `--backup` options), and keep the backups outside
the app's volume. Encrypt `totp_secret` at rest with a key from the environment (a `_FILE` secret like the hash), so a
database copy alone isn't enough. `chown 10001 admin-hash; chmod 400` in the deploy notes.

### M4-13 · LOW · new parsers of untrusted text, and no fuzz case

**Where.** `read_pending` (`second.odin:47-61`), envadmin's `read` (`envadmin.odin:122-135`), `totp.decode` and
`totp.verify` (`totp.odin:35-48`, `:70-90`), `hash_code` (`accounts.odin:218-230`) and `password.decode`
(`password.odin:216-255`) take request or cookie text. Each has unit cases; none has a fuzz target, and M3-09's
(`ws_field`) is still open.

**Scenario.** M4-02 is what a few minutes of fuzzing `read_pending` finds.

**Fix.** A fuzz target per parser in the nightly (§19.2.1), starting with the two MAC readers; the `=` cases into the
unit tests now.

### M4-14 · NIT · `Login.name` is a username's size holding a display name

`Login.name` is `[accounts.MAX_USERNAME]byte` (64, `routes.odin:106`), and `new_login` copies `u.display` into it
(`:120`): a display name of up to 40 runes is up to 160 bytes, so audit entries for sign-ins and step-ups cut such a
name at 64 bytes, mid-rune. Size it `4 * accounts.MAX_DISPLAY`, as `Hashing.display` is (`members.odin:43`).

### M4-15 · NIT · the audit filter is cut by byte

`audit.filter`'s `cap` (`audit.odin:28-31`) slices at 64 bytes, which can split a rune (CLAUDE.md: text cut from user
input is cut by rune). Harmless (the filter then matches nothing), but the rule is the codebase's.

### M4-16 · NIT · entries that say less than they could

A revoke is logged as `accounts.revoke` whether or not it ended anything (`closed`, `routes.odin:362-363`; the store
deletes only the member's own rows, so a foreign hash ends nothing and is still logged as a success). An invite's
creation (`admin.odin:265`, target `{"invite", 0}`), its withdrawal (`:309`) and its use (`members.odin:200-201`,
`invite=yes`) carry no id, so the log can't say which invite let whom in. A short prefix of the invite's hash in
`meta` for all three would.
